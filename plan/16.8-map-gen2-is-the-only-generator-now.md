# Phase 16.8 — `map-gen2` is the only generator now

> See [How it went](#how-it-went) at the end, which is where the shape it really took is written
> down. Everything above that section is the plan as it was written, including the parts the work
> proved wrong — the prediction next to the outcome is the point.

**Goal:** the `map-gen` crate and its `gen-map` command are gone, `map-gen2`'s own comments no
longer depend on a crate that does not exist to make sense, and `cargo test --workspace`/
`doc-check`/`regen-expected --check` all stay green.
**Depends on:** 16.7 — the point at which `map-gen2` reached full CLI parity with `map-gen`
(a file or the command line, either way, no editor required), which is what makes `map-gen`
genuinely redundant rather than merely older.
**Size:** S.

## Why now

Because two generators earn their keep only if a real map wants each one, and none does: nothing
in the tree has ever needed noise-drawn relief and source-drawn relief side by side, `open-plain`
is the only committed map either has produced, and it was drawn by `map-gen`, once, and never
touched again. A crate nobody is choosing between is not a choice, it is upkeep — a second set of
tests to keep green, a second doc comment to keep in step with the loader, a second thing
`doc-check`'s generator-edge check has to know the name of.

`map-gen`'s own map, `open-plain.ron`, is data and outlives the tool that first wrote it — the
same argument phase 16.5 made for why the file's own header comment is not a promise the command
would draw it again. Removing the crate touches nothing about the file already on disk.

It takes a half number because it is tooling in reverse: no state leaves, no table changes, no
step of the tick moves. Removing a crate is exactly the kind of change `ARCHITECTURE.md`'s own
checklist already names — *did you add, move, remove or reorder a tick step, or add a crate?* —
symmetrically true of taking one away.

## What gets built

### The crate leaves

`map-gen/` — `Cargo.toml`, `src/lib.rs`, `src/noise.rs`, `src/pipeline.rs`, `tests/draw.rs` — is
deleted outright, and with it the workspace's `members` entry naming it.

### The front door leaves with it

`xtask/src/gen_map.rs` is deleted; `xtask/src/main.rs` loses `mod gen_map;`, the `"gen-map"`
dispatch arm, and the `gen-map` line of `usage()`. `xtask/Cargo.toml` loses the `map-gen`
dependency and the comment introducing it, keeping only `map-gen2` and its own.

### `doc-check` learns there is one generator again

`source_files()`'s hardcoded crate-directory list drops `"map-gen"`.
`the_simulation_does_not_depend_on_the_generator`'s `GENERATORS` array shrinks to `["map-gen2"]`
— the array shape built in 16.6 stays, because it is exactly the shape this phase and that one
both needed and a future third generator would need again; only the one entry it was carrying for
`map-gen` goes.

### `map-gen2`'s own comments stop depending on a crate that is gone to make sense

Two different cases, told apart by whether the comment still teaches its rule once the thing it
compares against is unreadable:

- **A dangling citation.** `dice.rs` names `map-gen/src/noise.rs` and `map_gen::noise::field` by
  path — a reader following either finds nothing. These are reworded to state the seeding device
  in full, the way a comment that cites nothing already has to.
- **An identity that was never true on its own.** `lib.rs`'s crate doc calls `map-gen2` "`map-gen`'s
  sibling" and contrasts its `Report`/`places_for` against "the two crates" — both sentences
  describe a relationship that no longer has two sides. These are reworded to describe `map-gen2`
  on its own terms, not in contrast to something the reader cannot open.
- **A comparison that still teaches its rule without the comparison.** `repair.rs`, `classify.rs`
  and `pipeline.rs` cite `map-gen`'s choices as *why this crate chose the same thing* — excluding
  sub-sea neighbours from the steepest-step measurement, flattening water after classification and
  not before, building a real `Grid` rather than a second hand-rolled one. Each of these already
  states the rule in full before it ever mentions `map-gen`; the comparison is left in, as
  attribution, the way a comment can cite a paper or another project without the reader needing
  either open.

### The words leave with the algorithm they named

`noise`, `layer` and `ease` are removed from `GLOSSARY.md`'s "Words worth a definition": they were
added in 16.5 to explain `map-gen`'s value-noise pipeline specifically, no identifier anywhere in
the tree will carry any of them once that pipeline is gone, and none of the three was ever a rename
of something else — the "Retired words" section is for a name that changed and nothing else, which
this is not. `slope`'s entry stays exactly as written: "the step to the steepest neighbour" is
`map-gen2`'s own term too, not something only `map-gen` used.

### `ARCHITECTURE.md` loses the row and the plural

The `map-gen` row leaves the crate table. The sentence that used to bind two crates —
*"the same rule binds `map-gen` and `map-gen2`"* — binds one. `xtask`'s own row drops `gen-map`
from the subcommands it lists.

### The history stays history

`ROADMAP.md`'s `Done` rows for 16.5 and 16.6 are not rewritten: they are a ledger of what each
phase did at the time, and 16.5 genuinely did build `map-gen`. This phase adds its own row instead.
`plan/16.5-...md` gets a dated amendment at the end saying the crate it built was later removed,
and by what phase; `plan/16.6-...md` gets one too, since its own "Out of scope" section said
outright that the two generators were "siblings, not a migration" — true when written, and worth
recording that it stopped being true. Neither file's existing prose is rewritten; the amendment
goes below it, per the task skill's own rule for a document that is a record of a moment in the
past.

## Out of scope

**Renaming `map-gen2` to `map-gen`, or `gen-map2` to `gen-map`.** Nobody asked the surviving
generator to take the retired one's name, and doing it would rewrite the identity three already-
closed tasks (16.6, 16.7, and this one) describe it by, for a purely cosmetic gain.

**Regenerating or touching `open-plain.ron`.** It is data, not a claim about which tool could
redraw it, and phase 16.5's own "How it went" already explains why a generator is free to change
under a committed map without that map needing to move.

**Any change to the map file format, the loader, or `sim-data`.** Both generators only ever
produced a `MapDef` through the one format `sim-data` owns; removing one generator changes nothing
about the format the other still writes.

## Tests

1. ***The test that defines the phase.*** `cargo build --workspace` and `cargo test --workspace`
   succeed with `map-gen/` deleted and no `map-gen` member in the workspace — the whole tree
   compiles and passes with one fewer crate in it.
2. **`cargo xtask` has no `gen-map` command.** Running it is a clean "unknown command", not a
   panic or a stale binary from a cache.
3. **`gen-map2` still draws a map exactly as it did before**, from both `--sources <path>` and
   `--source` flags — this phase touches nothing in `map-gen2`'s algorithm, only its comments, so
   its own output cannot move.
4. **`doc-check` still passes**, with the shrunk `GENERATORS` array and the trimmed crate-directory
   list, and still fails if a `sim-*` crate is made to depend on `map-gen2` (checked by breaking it
   on purpose and putting it back, the same way 16.5 verified the original check).
5. ***The test that closes the phase.*** `regen-expected --check` is green before and after —
   this phase deletes a crate never reachable from `step()`, so nothing the simulation hashes
   could have moved.

## Verification

```sh
cargo xtask regen-expected --check   # before
```

```sh
cargo test --workspace
cargo clippy -p map-gen2 -p xtask --all-targets -- -D warnings   # sim-core carries a pre-existing,
                                                                   # unrelated dead-code warning
                                                                   # under --workspace, recorded in
                                                                   # 16.6's "How it went"
cargo fmt --all --check
cargo xtask gen-map2 --seed 7 --width 48 --height 32 --id smoke \
    --min-height 0 --max-height 31 --print \
    --source 4,4,mountain,3 --source 44,28,sea,5
cargo xtask regen-expected --check   # after: still green
cargo xtask doc-check
```

**Done when:** `map-gen/` no longer exists, `cargo xtask gen-map2` still draws maps exactly as it
did, and every document that named `map-gen` either says so as history that is not rewritten or no
longer needs to say so at all.

## How it went

**One thing the plan under-specified turned out to matter: `map-gen2`'s own comments, not just the
tree's shared documents.** The plan named `dice.rs`'s dangling file-path citations and `lib.rs`'s
"sibling" framing explicitly, but building the removal out touched five files in `map-gen2`
(`lib.rs`, `dice.rs`, `classify.rs`, `repair.rs`, `pipeline.rs`), plus its `Cargo.toml` and
`tests/draw.rs`, plus `xtask/src/gen_map2.rs`'s own doc comment, which cited the now-deleted
`gen_map.rs` by name twice. Each rewrite kept the rule the comment was stating and dropped only the
comparison to a crate that could no longer be read — in one case (`dice.rs`) this surfaced a more
accurate attribution than the one it replaced: the blake3-then-`Pcg64` seeding device was always
`sim_core::rng`'s own, borrowed once by `map-gen` and once by `map-gen2`, and citing `sim_core`
directly is the truer statement either way.

**The `GENERATORS` array stayed a list of one, deliberately.** 16.6 generalised
`the_simulation_does_not_depend_on_the_generator` from a single constant to an array specifically
so a generator could join or leave the check by editing one line; using it exactly that way here,
rather than reverting to a bare `const &str`, is the array earning the reason it was built. The
"break `sim-data`'s manifest on purpose" verification 16.5 first used was repeated once more:
adding `map-gen2 = { path = "../map-gen2" }` to `sim-data/Cargo.toml` was caught and named
correctly, and the manifest was put back.

**Word removal has no precedent in this tree, and `noise`/`layer`/`ease` are gone rather than
retired.** `GLOSSARY.md`'s "Retired words" section is explicit that it holds renames and nothing
else — "in every case it was the name that changed and nothing else" — so a concept leaving
entirely, with no replacement name, does not fit there. The three entries were deleted outright
from "Words worth a definition" instead. `slope`'s entry needed no change: "the step to the
steepest neighbour" is `map-gen2`'s own term now, not something it borrowed.

**`ROADMAP.md`'s `Done` rows for 16.5 and 16.6 were left exactly as written.** They are a ledger of
what each phase did at the time it did it, not a live index of current capability, and 16.5
genuinely did build `map-gen`. The amendments recording its removal live where the plan said they
would: a dated blockquote at the end of `plan/16.5-...md`, and one after `plan/16.6-...md`'s own
"Replacing `map-gen`" paragraph, which is the specific sentence the removal made no longer true.

**Everything else held.** `map-gen/` is gone, `gen-map` is an unknown command, `gen-map2` draws an
identical map to the one it drew before this phase (checked by running the same seed, size and
sources both before and after the removal and diffing the output), and `cargo test --workspace`,
`cargo fmt --all --check`, `cargo xtask doc-check` and `cargo xtask regen-expected --check` are all
green — the last one unchanged before and after, since nothing this phase touched was ever
reachable from `step()`. `cargo clippy -p map-gen2 -p xtask --all-targets` is clean; the workspace-
wide `-D warnings` run still cannot get past `sim-core`'s pre-existing `WalksToTheEnd` warning, for
the same reason 16.6 and 16.7 both recorded it and left it alone.
