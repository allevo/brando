# Phase 16.6 — Sources claim a map, and shape what they claim

> See [How it went](#how-it-went) at the end, which is where the shape it really took is written
> down. Everything above that section is the plan as it was written, including the parts the work
> proved wrong — the prediction next to the outcome is the point.

**Goal:** `cargo xtask gen-map2 --seed <n> --width <n> --height <n> --id <name> --min-height <n>
--max-height <n> --sources <path>` writes a map that `load_map_by_id` accepts with no hand editing.
**Depends on:** 16.5 — the map file format, and the check that keeps a generator outside the
simulation's dependency graph.
**Size:** L.

## Why now

`map-gen` draws a map from noise, and a noise field is a poor tool for saying *there is a mountain
range here and a coast there*: every landform in it is an accident of the lattice, nudged only by a
border falloff. This phase adds a second, independent generator that starts from the opposite end —
a short list of points, each already saying what it wants to become and how strongly — and grows a
map outward from them by direct competition. Point placement is designer intent in a way a noise seed
never is, and the two generators are worth having side by side rather than one replacing the other:
different maps will want different tools, exactly the way `open-plain` and the hand-drawn
`river-valley` already sit side by side.

Everything phase 16.5 already argued for a generator applies unchanged and is not re-argued here: a
generator inside the core would become a frozen part of the determinism contract, so it lives outside
as a crate `xtask` alone may depend on, and `doc-check` refuses any other. The map format, its
loader, and `sim_data::save_map`'s "write nothing the loader would refuse" guarantee are also already
built; this phase spends none of its effort on them and all of it on the second algorithm.

It takes a half number for the reason 16.5's own did: it is tooling. It introduces no state, changes
no table, and touches no step of the tick.

## What gets built

### The crate, and what it promises

`map-gen2`: a library, `sim-core` and dice for dependencies, and — the same promise `map-gen` makes
— nothing that can touch a disk.

```rust
pub struct Source { pub point: sim_core::TilePos, pub kind: SourceKind, pub strength: u16 }
pub enum SourceKind { Mountain, Land, Sea }
pub struct DrawInput {
    pub seed: u64, pub sources: Vec<Source>,
    pub width: u16, pub height: u16,
    pub min_height: u8, pub max_height: u8,
    pub id: String,
}
pub fn draw(input: &DrawInput) -> Result<Drawn, DrawError>;
pub fn report(drawn: &Drawn, data: &sim_core::DataSet) -> Report;
```

`DrawInput` is a struct and not `map-gen::draw`'s bare positional arguments, because this draw has
seven independent inputs, one of them a list, and a seventh positional argument is exactly the
signal a struct exists for.

`Drawn { def, repair }` and `Repair { regions_before, tiles_drowned }` are the identical shapes
`map-gen` already carries, for the identical reason: after the repair there is always exactly one
walkable region, so `MapDef` alone can no longer say how many there were before it.

`DrawError` enumerates every way a `DrawInput` can fail, and stops there: a size the grid will not
hold; a height range that does not fit `0..=Tile::MAX_GROUND_HEIGHT` or does not order (`min <=
max`); a height range that excludes height 8, the level every tile starts at, since that would make
the input contradict the algorithm's own first step; an empty source list; a source outside the
grid; two sources sharing a tile; and a seed whose sources leave no land standing after the repair.
Seven variants, validated in that order, before any of the three passes below run at all.

### Step 1 — sources compete for tiles

Each source keeps two sets: `A`, the tiles it has claimed, seeded with its own input point; and `B`,
the untransformed neighbours of `A` not yet claimed by anyone. Sources act in the order they were
given. Let `max_strength` be the largest strength among them. Starting from round 0, a source gets a
turn on a round only when `round % (max_strength - strength + 1) == 0` — the weaker a source, the
longer between its turns. On its turn a source with a non-empty `B` draws one tile from it uniformly
at random, moves it into `A`, gives it the source's type, pushes every unclaimed neighbour of that
tile into its own `B`, and removes the tile from every other source's `B` — it is no longer anyone
else's to claim. This repeats until every tile has an owner.

No `HashMap`/`HashSet` anywhere (workspace-disallowed): ownership is one `Vec<Option<SourceId>>`
indexed by tile — which *is* every source's `A` at once — plus, per source, a claim-order `Vec` and a
frontier structure pairing a `Vec` of pending tiles with a same-length position index, so removing a
specific tile from a frontier is O(1) rather than a scan.

Termination is not an assumption: the grid is fully connected and has no obstacles yet, so whenever
tiles remain unclaimed the boundary of the claimed region is non-empty, and a boundary tile sits in
some source's `B` by construction. Every source's turn period is finite, so the loop provably ends
within `tiles × (max_strength + 1)` rounds — backed by a `debug_assert!` round cap as a safety net on
that proof, not a substitute for it, the same convention the codebase already uses around a proven
invariant (`sim-core/src/grid.rs`'s `unreachable!()` on the terrain field, with the comment that
proves it).

### Step 2 — mountains and seas shape their own ground

Every tile starts at height 8. Only mountain and sea sources act in this step; a tile a `Land`
source claimed keeps height 8 for good. Each participating source picks one tile of its own `A`
uniformly at random as its origin, and keeps a growing set `C`, seeded with that one tile. The same
turn schedule as step 1 governs when a source acts, restarting the round counter at 0.

On its turn, a source first rolls, independently for every tile currently in `C`: with probability
exactly `1/(d+1)`, where `d` is the Manhattan distance from that tile to the source's origin, the
tile's height moves one step towards the source's extreme (up for a mountain, down for a sea),
never past the caller's `max_height`/`min_height`. Then, regardless of whether any roll succeeded,
the source adds to `C` every neighbour of `C`'s tiles that belongs to its own `A` and is not already
in `C`. A source stops acting once `C` equals `A` — growth, not height convergence, is what ends its
turn, so a source whose neighbourhood has stopped rolling successfully keeps growing `C` until its
whole territory is covered regardless. Step 2 as a whole ends once every mountain and sea source has
reached that state.

This terminates for the same reason step 1 does: a source's `A` is connected (every tile joined it by
neighbouring an already-claimed one), `C` only ever grows and stays a subset of `A`, and as long as
`C` is a strict subset some tile of it neighbours a tile of `A` it has not yet reached — so every act
adds at least one tile to `C`, unconditionally, until `C = A`.

The probability roll is integer arithmetic throughout — a draw uniform in `0..=d`, success on 0 —
never a float, satisfying the workspace's `float_arithmetic = "deny"` lint the same way `map-gen`'s
own fixed-point noise does.

### Step 3 — height becomes terrain

Two thresholds, both named constants, and no others: below height 8, water; at or above it, land;
and among the land, a tile whose **step to the steepest neighbour** — `map-gen`'s own term, reused
rather than reinvented, and never called a slope, since `GLOSSARY.md` already gives that word one
meaning and reusing it for a second is the exact failure the entry warns against — reaches 2 or more
is rock, otherwise plain. The steepest-neighbour measurement excludes neighbours below sea level, the
same fix 16.5 found the hard way: the ground keeps falling under the water, so counting the drop into
the sea reads every coastline as a cliff. Water then flattens to height 0, after classification and
not before, for the same ordering reason 16.5 already wrote down.

This phase adds no third, absolute "always rock above height N" rule the way `map-gen` has — the
user's own specification names exactly two thresholds, and a third would be scope nobody asked for.
A perfectly flat plateau at the ceiling height classifies as ordinary plain.

### The repair, inherited unchanged in shape

Nothing in the three steps above guarantees the walkable ground comes out in one connected piece — a
ring of sea sources, or an unlucky run of mountain claims, severs a map exactly as easily as noise
can — and the loader refuses a severed map. So the same flood-fill repair 16.5 built runs last:
find every walkable connected region, keep the largest (ties broken by lowest tile index, the order
regions are discovered in), drown the rest. Built here against a real `Grid` rather than a
hand-rolled adjacency function: unlike `map-gen`'s pipeline, which has no `Grid` to work with at the
point it needs one, this pipeline can afford one throwaway `Grid::new(width, height, Plain)` up
front purely for its geometry, and thread it through every pass instead of a second adjacency
implementation kept in sync with `Grid::neighbors4` by convention alone.

### The front door, and where the sources come from

```
gen-map2 --seed <n> --width <n> --height <n> --id <name> --min-height <n> --max-height <n> \
         --sources <path> [--out <path>] [--print]
```

Everything else about the front door matches `gen-map`'s: parse the flags, load the tables, call
`draw`, print `report`, call `save_map`. The one genuinely new question is where a *list* of sources
comes from, since it does not fit on a command line the way four scalars do. It is a small RON file,
and `xtask` owns reading it rather than `map-gen2` — the same principle `map-gen`'s own doc comment
already states for the output side (the crate that *consumes* a format for a purpose owns it), applied
to the input side this time. `map-gen2` gains no `serde`/`ron` dependency of its own; its real API is
`Vec<Source>`, and the RON shape is xtask's translation of a file into that.

### Nothing the simulation loads may depend on either generator

`doc-check`'s existing check, `the_simulation_does_not_depend_on_the_generator`, currently names one
crate. It generalises to a small list of generator crates, checked in the same loop against the same
three manifests, so the rule reads as what it now is — a rule about a family, not one crate — rather
than happening to still work because `"map-gen2"` contains the substring `"map-gen"`. The other trap
16.5 already found the hard way applies again unchanged: `doc_check.rs`'s source-file walk is a
hardcoded list of crate directories, and a crate missing from it escapes every check silently. Adding
`map-gen2` to both spots belongs in the same commit that creates the crate.

### The words

`source` and `strength` are the user-facing vocabulary the algorithm is specified in, and both are
plain enough to earn their place in `GLOSSARY.md` directly. The tick-scheduled loop that both steps
share needs a name of its own for its counter, and it cannot be `tick`: `GLOSSARY.md` already gives
that word exactly one meaning, the `Calendar`'s simulation-time unit, and a second meaning for it is
the same failure the `slope` entry already guards against. `round` is proposed as the plain word for
one pass of that loop — flagged here explicitly, since it is the one word in this phase invented
rather than taken from the algorithm's own specification, and the naming rule asks that it be asked
about rather than assumed.

## Out of scope

Everything 16.5 already put out of scope for a generator and has not changed: rivers, erosion, a
rock field of its own, trees and what stands on the ground, what the soil is worth, roads, buildings,
a starting city, a `--check` that redraws committed maps and compares, and drawing a map at play time
from a recording. None of those arguments are re-made here; they apply to this generator exactly as
they apply to the first one.

**An absolute rock-height rule.** `map-gen` has one (`ROCK_HEIGHT`, rock above a fixed ceiling
whatever the slope); this generator's own specification names only the two thresholds in step 3, and
adding a third that was not asked for is scope this phase does not take.

**Replacing `map-gen`.** The two are siblings, not a migration. Nothing about `open-plain` or
`river-valley` changes, and nothing requires this generator's output to ever be committed at all —
that is a choice for whoever draws with it, exactly as it was for phase 16.5's own noise.

## Tests

1. ***The test that defines the phase.*** Across a sweep of seeds, sizes and source lists, every map
   `draw` produces survives `render_map` → `parse_map` → `validate_map`, through the rendered text and
   not the arrays it came from — the loader is the only honest judge of whether a generated map is
   real.
2. **Every tile ends up with exactly one owner**, and every source's claimed tiles stay disjoint from
   every other's, for the whole run of step 1.
3. **A weak source still eventually claims ground.** Among strong peers, a source with the lowest
   strength in the list still gets turns and still grows, however slowly.
4. **Relief only ever touches what a mountain or a sea claimed.** A tile a `Land` source owns stays at
   height 8 for the whole of step 2, and every touched height stays within the caller's declared
   `min_height..=max_height`.
5. **Step 2 terminates with every participating source's `C` equal to its `A`** — the stated stopping
   condition, checked directly rather than inferred from the loop simply having returned.
6. **The steepest-neighbour measurement ignores water**, pinning the inherited fix by name: a shore
   tile next to a much lower sea tile is not rock on that account alone.
7. **One walkable region, always**, and the repair only ever drowns land, never creates it — the same
   property 16.5 pinned for its own repair, asked of this one.
8. **A seed is the whole of what makes a map.** The same seed, sources and size twice give an equal
   map; a different seed does not, on a size large enough that the comparison means something.
9. **Every way a source list can be wrong is refused by name** — one assertion per `DrawError`
   variant beyond the two `map-gen` already has: out of bounds, a duplicate origin, an empty list, a
   height range above the tile's real ceiling, a height range excluding height 8.
10. **The corners do not panic.** 1×1, and both extremes of the largest side the grid allows.
11. **Somewhere to put the largest building**, on the specific source configuration eventually chosen
    for commit — read through the real `Grid::slope_over` and the real `max_build_slope`, so the tool
    and the game cannot disagree about what is placeable. Not a full sweep: unlike a noise field, an
    arbitrary source list is not guaranteed to leave anywhere buildable at all.
12. **Nothing the simulation loads depends on either generator.** The generalised check, run with the
    others.
13. ***The test that closes the phase.*** `regen-expected --check` is green **before and after**. This
    phase adds no core code, no table value and no step to the tick, so nothing the simulation hashes
    may move at all — 16.5's own closing test, asked of a second generator.

## Verification

```sh
cargo xtask regen-expected --check
```

```sh
# After.
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
cargo fmt --all --check
cargo xtask gen-map2 --seed <n> --width <n> --height <n> --id <name> \
    --min-height 0 --max-height 31 --sources <path>.ron --print
cargo xtask regen-expected --check   # still green: nothing may have moved
cargo xtask doc-check
```

Draw several seeds and source layouts before choosing whether to commit any of them, and choose on
the report's places-for-a-building figure — with the same caveat 16.5's own "How it went" recorded
about that number: it can miss a map that is visually broken but numerically fine, so look at the
printed terrain too, not only the count.

**Done when:** the tool writes a map with no hand editing that `load_map_by_id` accepts, the
generalised check proves that no crate the simulation loads depends on either generator, and
`regen-expected --check` is green both before and after — the last of which is what proves that a
second generator living outside the core changed nothing inside it.

## How it went

**`DrawError::NoLandLeft` turned out not to exist, and the reason is worth recording at length,
because it was not a coding mistake — it fell straight out of the growth rule the user had already
settled before this task was opened.** The plan carried it by analogy with `map-gen`'s own error of
the same name, on the assumption that a seed could, in principle, submerge an entire map the way a
noise field sometimes does. Building step 2 out fully proved the opposite: a source's `C` grows by
one BFS layer per act, and the roll only ever runs on the tiles `C` already held *before* that act's
growth — so the tiles a growth phase adds are rolled on for the first time only on the source's
*next* act, and a source that has just reached `C == A` never gets a next act. The tiles added on
that final, terminating growth act are therefore never rolled at all, and stay at height 8 forever —
which step 3 always classifies as land. Every source, without exception (a `Land` source never touches
height in the first place; a source whose whole territory is one tile never acts at all; a source with
a larger territory always has a final, un-rolled layer), guarantees at least one land tile. With at
least one source required by `NoSources`, this means **a fully submerged map is not a rare seed to
guard against here — it is not a reachable state at all.** `DrawError` shipped with six variants
instead of the plan's seven, and the check that would have returned the seventh is now a
`debug_assert!` carrying the proof, in the same style `Tile::terrain()`'s `unreachable!()` already
uses in `sim-core` for a different provably-closed case. The corresponding planned test ("a seed with
only sea sources leaves no land and is refused") was dropped for the same reason: it would have been
asserting something the algorithm cannot do.

**A pre-existing, unrelated problem surfaced and was left alone.** `cargo clippy -p map-gen2
--all-targets -- -D warnings` cannot currently pass — not because of anything in `map-gen2`, but
because `sim-core/src/coverage.rs`'s `WalksToTheEnd` marker struct is only ever used as a generic type
parameter and never literally constructed, which trips the dead-code lint the moment `sim-core` is
built as a plain library dependency rather than with its own tests enabled. This is not a regression
this phase introduced: `cargo clippy -p map-gen --all-targets -- -D warnings`, run against the
untouched, already-shipped `map-gen` crate, fails identically. `cargo clippy -p map-gen2 --all-targets`
(without `-D warnings`, since the workspace-wide `-D warnings` run cannot get past `sim-core` at all)
is clean once every lint clippy actually raised in this crate's own files was fixed
(`manual_is_multiple_of`, `needless_range_loop`, `useless_vec`, and a rustdoc lazy-blockquote-
continuation warning from a doc comment that happened to start a line with `>=`). Fixing
`sim-core`'s own issue was out of scope for a phase that promised to touch nothing inside the core,
and is left for whoever next needs a green `cargo clippy --workspace --all-targets -- -D warnings`.

**Everything else in the plan held.** The crate layout, the public types, the three-pass pipeline plus
the repair, the `dice.rs` seeding device, the `gen-map2` front door with sources supplied as a RON file
`xtask` owns, both `doc_check.rs` edits, and the `ARCHITECTURE.md`/`GLOSSARY.md` updates all went in
exactly as designed. `RULES.md` was consciously left untouched: `map-gen2`'s sea level and rock-step
threshold are generator-internal constants nothing in the simulation reads, the same treatment 16.5
already gave `map-gen`'s own constants. `cargo test --workspace`, `cargo fmt --all --check`,
`cargo xtask doc-check` and `cargo xtask regen-expected --check` are all green, the last one unchanged
both before and after this phase's work — proving a second generator living outside the core changed
nothing inside it. A hand-run of `cargo xtask gen-map2` against a five-source layout (two mountains,
two seas, one land, at the corners and centre of a 48×32 map) wrote a map that round-tripped through
the real loader and reported sensible places for every building footprint in the table.
