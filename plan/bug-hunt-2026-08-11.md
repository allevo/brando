## 1. A food provider that produces nothing passes every check, then starves the houses it covers — permanently and silently

**Where:** `sim-core/src/data.rs:539`, in `DataSet::check_food_capacity`.

```rust
let (Some(output), Some(max_stock)) = (def.output_per_tick, def.max_stock) else {
    continue;                              // <- "not my problem"
};
```

Both missing fields mean the provider sustains **zero** residents, so any positive
`capacity_per_level` ought to be reported. Instead the building is skipped entirely.

`sim-data`'s `validate_output` (`sim-data/src/validate.rs:586`) covers the neighbouring
case — output without stock is `ProducerWithoutStock` — but its `(None, None)` arm is
empty. So **capacity-without-output is caught by nothing at all**, in either crate.

### Reproduction

A dataset whose third building declares the food service with `capacity_per_level: [20]`,
`output_per_tick: None`, `max_stock: None`; one well, one house, one road, 60 ticks:

```
inconsistencies() == []            <- passes validation
covered_but_unfed = 61             <- 61 house-ticks assigned to it, never fed
house food-served = true, satisfaction = [100, 100], level = 2
```

### Why it matters more than "bad data in, bad game out"

- The house's food satisfaction climbs to the ceiling and it **levels up on starvation**,
  because `satisfaction::update` reads `House::served`, which since phase 12 means
  "covered" and not "it ate" (A9). Nothing in the game state records that it never ate.
- It is **unrecoverable in play**. The phantom provider wins the contest for those houses
  (`coverage.rs:242` — first provider in `BuildingId` order), so building a real farm
  afterwards cannot take them over. That is precisely the absorbing hunger state A5 was
  dissolved to remove.
- `CapacityBeyondOutput` is the check that exists for this, and its own doc comment
  (`data.rs:513`) states the rule it is meant to guarantee: *"a house covered by the food
  service always eats"*. The hole is in the guard itself.
- `FoodTotals::covered_but_unfed` — the counter that would shout — is only ever asserted
  in tests. The game never looks at it.
- `DataSet::inconsistencies` is also what protects `sim-core`'s own fixture
  (`tests/common/mod.rs`), which never goes through `sim-data`. So the same hole means the
  fixture could drift onto this shape and `covered_means_fed` would be checking a property
  the game does not have.

### Suggested fix

Do not skip. Treat a missing output or stock as sustaining zero:

```rust
let available = match (def.output_per_tick, def.max_stock) {
    (Some(o), Some(m)) => o.to_millis().min(m.to_millis()),
    _ => 0,
};
```

and let the existing loop over `capacity_per_level` report `CapacityBeyondOutput { .. ,
sustainable: 0 }`. The message already reads correctly for that case.

Worth a regression test in `sim-data/tests/tables.rs` (a broken fixture alongside
`unsustainable_capacity.ron`) and one in `sim-core/tests/invariants.rs` asserting that
`inconsistencies()` is non-empty for such a dataset.

## 2. `Stream::fill_bytes` counts one draw whatever the length, so the state hash goes blind on the RNG

**Where:** `sim-core/src/rng.rs:115`, and the assumption it breaks at
`sim-replay/src/hash.rs:110`.

```rust
fn fill_bytes(&mut self, dst: &mut [u8]) {
    self.count_draw();            // one, regardless of dst.len()
    self.rng.fill_bytes(dst);
}
```

`rand_pcg` 0.9's `Lcg128Xsl64::fill_bytes` is `impls::fill_bytes_via_next`, which steps the
generator `ceil(len / 8)` times. (`next_u32` and `next_u64` are both exactly one step, so
those two are fine.)

`hash_world` hashes only `draws` per domain, on the assumption written at `rng.rs:75`:
*"For a given seed, the number of draws uniquely determines the generator's state, so
hashing (seed, draws) covers the RNG's state without having to serialise its internals."*
That is false as soon as anything calls `fill_bytes`.

### Reproduction

Two `RngSet`s from seed 7, one filling 8 bytes, the other 64:

```
draws a = 1, draws b = 1, same state = false
next a = 1053976881200921267, next b = 8316991403223961636
```

Equal draw counts, divergent generator states, identical state hash.

### Why it matters

Latent today — no system in M0/M1 draws yet, which is why
`different_seeds_give_different_hashes` is still `#[ignore]`d. But `RngSet::get` is `pub`
and hands out a `&mut Stream` implementing `RngCore`, so `fill_bytes` is reachable from any
core system. Phase 15 (migration) is the first real user of `RngDomain::Migration` and the
first chance to trip over this. The consequence is the worst kind for this project: the
recorded replays stop protecting a divergence, so it surfaces months later as an
inexplicable balancing bug — exactly the failure phase 08 exists to prevent.

### Suggested fix

Either count the real number of steps:

```rust
fn fill_bytes(&mut self, dst: &mut [u8]) {
    self.draws = self.draws.wrapping_add(dst.len().div_ceil(8) as u64);
    self.rng.fill_bytes(dst);
}
```

or drop the `(seed, draws)` shortcut and hash the `Pcg64` state directly. The first keeps
the existing hash shape; note it changes no recording today, since `draws` is 0 everywhere.

A unit test in `rng.rs` — two streams, same seed, `fill_bytes` of different lengths, assert
the draw counts differ — pins the invariant the doc comment claims.

## 3. `World::walkers` is state and is not in the state hash

**Where:** `sim-replay/src/hash.rs:37-119` (the omission), `sim-core/src/world.rs:507`
(the canary that cannot fire), `sim-replay/tests/expected.rs:288` (the test that cannot
see it).

`hash_world` covers tick, dataset hash, difficulty, grid dimensions, tiles, buildings,
houses, economy and RNG positions. It never touches `w.walkers()`. Its doc comment lists
what is deliberately excluded — *"RoadNetwork, Coverage, DirtyFlags, FoodTotals"* — and
walkers is not in that list either. So it is neither hashed nor documented as excluded.

`world.rs:65` describes `Walker` as a real simulated entity per D3 (goods transport, trade
caravans, immigrants), i.e. state, in contrast to the decorative walkers of D2 that live in
the renderer. `PopulationTotals`, by comparison, carries an explicit "outside the hash for
the same reason" note at `world.rs:165`. Walkers carries nothing.

Both guards are already defeated, which is the part that matters:

- `World::field_canary` (`world.rs:507`) already lists `walkers: _`, so it will not stop
  compiling when M3 starts populating the field. The reminder is spent.
- `the_hash_covers_the_whole_state` has no walkers perturbation, and cannot easily get one:
  there is no `walkers_mut` under `test-util`.

So the moment a walker exists in the state, the recordings are blind on it and nothing goes
red. This is the known A3 risk landing in the one place its two mitigations both miss.

### Suggested fix

Add walkers to `hash_world` now, while the vector is empty and the change moves no
recording (hashing a `0u64` length prefix costs one block and changes every hash once —
cheaper now than after phase 14). Add a `walker_mut`/`push_walker` under `test-util` plus
the matching perturbation. If the decision is instead that walkers stay out until M3, write
that down in `hash_world`'s doc comment next to the other four, so the omission is a
decision rather than a gap.

## 4. A house with zero residents consumes no capacity, so on `hard` a provider serves unboundedly many

**Where:** `sim-core/src/coverage.rs:311`, in `pick_within_capacity`.

```rust
left = left.checked_sub(residents)?;      // residents == 0 always succeeds
```

On the `hard` profile every house is born with `starting_residents_per_house: 0` (phase 11,
`difficulty.ron`), so every house in range is picked whatever the capacity — including from
a provider whose capacity is itself 0.

### Reproduction

Fixture's `small_well` (capacity 4 residents), seven houses on `hard`:

```
small well capacity 4 residents, 7 empty houses, 7 served
```

### Why it is worth a decision rather than a fix

Defensible on its own terms: capacity is counted in residents (A12, `coverage.rs:282`), and
an empty house genuinely weighs nothing. But coverage is also what feeds satisfaction, so
on `hard` a single 4-resident well takes an entire district to the top rung of the ladder
for free, which is the opposite of what that profile is for.

And when phase 15 lands, every one of that unbounded backlog of assignments becomes a real
claim on a provider sized for four. Whatever the answer — cap the candidate count, charge a
minimum of one per house, or accept it and say so — it is cheaper to settle before
migration moves the recordings than after.

Note that every invariant proptest runs on `world()`, i.e. `easy`; `population_is_consistent`
(`tests/invariants.rs:128`) even hardcodes `house_count * RESIDENTS_PER_HOUSE`. Nothing in
the property suite exercises `hard` at all.

## 5. `remove_building` mutates partially

**Where:** `sim-core/src/tick.rs:222-244`.

```rust
let Some(b) = world.buildings.remove(id) else { return; };
let Some(def) = world.data.def(b.kind) else { return; };   // already removed
```

By the second line the building is out of the `SlotMap`. If the `def` lookup fails, the
function returns having done half the job: tiles stay occupied, `buildings_by_origin` keeps
a dead id — so `World::occupant` resolves to a `BuildingId` with no building, which
`no_overlap` reports as *"points at a dead building"* — `forget_coverage` is skipped, and
coverage is never invalidated.

Unreachable through play: the kind was validated when the building was placed and the
dataset is immutable behind an `Arc` for the life of the world. But it is the one place in
the file that breaks the discipline `place_road` and `place_building` hold explicitly
("from here on nothing can fail: no partial mutation", `tick.rs:96` and `tick.rs:160`).

### Suggested fix

Read `def` before removing, or fall back to `(1, 1)` for `clear_tiles` the way
`remove_house` does at `tick.rs:253`, and run the rest unconditionally.

## 6. Three small ones

### `Rules::ticks_per_year` is an unchecked multiply

`sim-core/src/data.rs:106`:

```rust
pub const fn ticks_per_year(&self) -> u32 {
    self.ticks_per_month * self.months_per_year
}
```

`is_month_boundary`, fifty lines below, guards its divisor with the comment *"a modulo by
zero is a panic, and the core does not panic on data"* (`data.rs:158`). The same argument
applies to this multiply. Tables loaded through `sim-data` are guarded by the `checked_mul`
in `validate_rules`; hand-built fixtures — `sim-core/tests/common/mod.rs`, `bench.rs`'s
`with_unlimited_treasury` — are not.

### The overflow guard reports the wrong thing

`sim-data/src/validate.rs:210`:

```rust
if r.ticks_per_month.checked_mul(r.months_per_year).is_none() {
    rep.push("rules.months_per_year", ValidationErrorKind::TooSmall { min: 1, found: 0 });
}
```

An overflow is reported as "expected at least 1, found 0", which describes a different
problem and points at a field that may well be fine. `the_report_messages_are_stable`
asserts on these strings, so whoever hits it gets a message that actively misleads. Worth
its own `ValidationErrorKind` variant, or at least a `TooLarge`.

### `levels::review` evicts everyone when the destination level is off the table

`sim-core/src/levels.rs:104`:

```rust
let capacity = rules.max_residents(to).unwrap_or(0);
```

`decays()` returns `true` for a level the table does not contain (`levels.rs:139`, and
deliberately so — coming down converges on a level that exists). But if `to` is *also* off
the table, the fallback capacity is 0 and every resident is evicted in one review, which is
a population wipe rather than a convergence.

Unreachable in play — `rises` is bounded by `top_house_level`, `residents_within_capacity`
would flag a house at an off-table level, and levels only ever start at 1 — so this is only
reachable via `test-util`'s `house_mut`. Still, `0` is a strange fallback for "unknown
capacity"; leaving `residents` alone until the house reaches a level that exists would
match the stated intent.

## What I checked and found clean

For the record, so a later pass does not redo it:

- **D4 prohibitions.** No `HashMap`/`HashSet`/`thread_rng`/float anywhere in the `sim-*`
  crates; `clippy.toml` enforces all four and clippy is clean. RNG seeds derive from the
  domain *name*, and `sequences_are_reproducible_with_the_expected_values` pins the values
  by hand.
- **`HousesByTile`'s counting sort** (`coverage.rs:89`). The three passes and the
  right-shift at the end are correct, including the `offsets[tiles]` sentinel.
- **`bfs_roads` and `Visited`** (`network.rs:195`). The generation marker, the wrap reset,
  the wrong-size rebuild, and the `d == max` break are all sound; `d` cannot overflow
  because the break precedes the increment and depth is bounded by the tile count. The
  three tests in that module cover the scratch-reuse class properly.
- **Food conservation.** `produced == consumed + lost_to_full_stock + lost_to_demolition +
  stock` holds as an exact equality, and with the *production* tables the capacity/output
  relation really does imply "a covered house always eats" — 400 output, 20 per resident,
  capacity 20. Finding 1 is about a shape the tables do not currently have.
- **Coverage contention and priority.** `(distance, TileIdx, HouseId)` is a total order;
  contested houses are filtered before filling, so a taken house does not consume the
  runner-up's capacity; `pick_within_capacity` skips rather than blocks, and its table test
  covers the mixed-population rows that M0 could not observe.
- **Step 6 ordering.** 6.1 before 6.2, review on month boundaries only, decay evaluated
  before rise in one pass, eviction as the only `residents` write and the only coverage
  invalidation. The hysteresis holds, and `the_level_shows_no_oscillation_with_constant_services`
  really does exercise it (the served corner at 20..27 is outside the generator's 0..14
  window, so it is not vacuous).
- **Event deltas.** `house_snapshot` is sorted and binary-searched correctly; newborn
  houses compare against `Desperate`, which validation makes true by construction
  (`mood_thresholds` strictly ascending and above zero); mood is computed against the
  post-review level on purpose.
- **Dirty flags.** Every mutation that can change coverage invalidates it — placement,
  demolition, road rebuild, eviction — which is what `coverage_equivalence` checks, and it
  passes. `nothing_is_recomputed_while_the_population_does_not_move` confirms the negative
  half.
- **Replay plumbing.** Header version gate, dataset-hash gate, difficulty by textual id
  with no fallback, `checkpoints` stride arithmetic including a non-multiple `until`.
- **Scenario behaviour.** `minimal` and `hunger` over 360 ticks both match their
  descriptions; `hunger`'s 7/8 water is the well's range of 12 (the house at x=15 sits at
  distance 13), not a capacity bug, and its 5/8 food is the farm's capacity of 20 residents
  exactly.
