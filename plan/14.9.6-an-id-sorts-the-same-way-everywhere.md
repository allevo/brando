# Phase 14.9.6 — An id sorts the same way everywhere

> See [How it went](#how-it-went) at the end, which is where the shape it really took is written
> down. Everything above that section is the plan as it was written, including the parts the work
> proved wrong — the prediction next to the outcome is the point.

**Goal:** a task id is written so that byte order and the order the numbers really run are the same
order, and `doc-check` refuses one that is not.
**Depends on:** 14.7, for the numbers being read component by component, and 14.9.5, for the skill
that states how to choose one.
**Size:** S — one check, one skill section, one renumbering.

## Why now

Phase 14.7 settled how two half numbers compare: component by component, as whole numbers, so
`14.10` follows `14.9`. That is right, and it is what `doc-check` does. What it does not do is
make anything *else* agree. `ls`, the editor's sidebar and the file list on the web compare bytes,
and under byte comparison `14.10-...` falls between `14.1` and `14.2` — before `14.4`, before the
task it follows, before most of the phase it belongs to.

The tree grew exactly one such file, and it was the one teaching the task procedure: it sat at the
top of the fourteens, out of order, in every list a reader ever opens. Nobody reading `plan/` runs
`doc-check` first. A rule the checker keeps privately and the file system contradicts publicly is
worth less than one both agree on.

The fix costs nothing, because the depth is already there: `14.5.5` has sat between `14.5` and
`14.6` since the constitution was filed. The slot above `14.9` is `14.9.5`. Slots between two
phases were never going to run out at nine — they run deeper rather than wider, and that is the
part 14.7 predicted correctly and 14.10 spent instead.

## What gets built

**The rule.** A task id's first component is written with two digits, every component after it with
one. Byte order then agrees with numeric order for every name the plan directory can hold: `-`
(0x2D) sorts before `.` (0x2E), so a whole phase precedes its own half numbers, and a shorter id
precedes the ids that descend from it.

**The check.** `task_names_sort_the_way_the_numbers_run` in `xtask/src/doc_check.rs`, registered in
`run` beside the check that a task agrees with its name. It reads the leading run of digits and dots
from the **file name** — the name is what the file system sorts, so the name is what is checked —
and reports a component of the wrong width with a message that teaches the rule rather than naming
it. This is `CLAUDE.md`'s standing rule that an agreement the code has to keep is a check and not a
comment.

**The skill.** `### 1. Choose the id` states the shape and why byte order has to agree, and says
the checker refuses the second digit — so it is not a rule anyone has to carry around.

**The renumbering.** `14.10-writing-a-task-is-a-procedure.md` becomes `14.9.5-...`, front matter
and heading with it, and gets a dated amendment saying it was filed under the old number. Its frozen
prose is not touched. `14.7` gets an amendment too: its choice stands, and the convention on top of
it has narrowed.

**The worked examples.** `GLOSSARY.md` and three comments in `doc_check.rs` all use `14.10` to
illustrate component-wise comparison. They now illustrate a name the checker rejects, so each moves
to the pair that carries the rule: `14.5.5` between `14.5` and `14.6`, and `14.9.5` above `14.9`.

## Out of scope

The front matter `id:` string. `Task` keeps the id parsed, so `09` and `9` reach the check
indistinguishable, and it is the file name that determines where the file lands in a listing. The
check is about sorting and stops where sorting stops.

The numeric sort in `read_tasks` stays as it is. It would be tempting to delete it now that names
are written so byte order agrees — that would make the ordering depend on the convention holding
rather than on the numbers, which is the wrong way round.

## Tests

- A unit test beside `half_numbers_are_read_as_numbers`: the shape check accepts `09-x.md`,
  `14.4-x.md` and `14.9.5-x.md`, and rejects `14.10-x.md` and `9-x.md`.
- `half_numbers_are_read_as_numbers` loses its `14.9 < 14.10` assertion, which blesses a name the
  checker now rejects, and gains `14.9 < 14.9.5 < 15`. It keeps `09 < 10`, which is why comparing
  the components as numbers is needed at all.
- `xtask/tests/docs.rs` runs the whole checker over the real tree, so the renumbering is covered by
  the suite that already exists.

## Verification

```sh
cargo xtask doc-check
cargo test -p xtask
ls plan/
```

The last one is the test the whole task is for, and it is read by eye with no `--sort` flag helping:
the fourteens have to run `14`, `14.4`, `14.5`, `14.5.5`, `14.6`, `14.7`, `14.8`, `14.9`, `14.9.5`,
`14.9.6`, then `15`.

**Done when:** `cargo xtask doc-check` is green, a task named `14.10-...` makes it red, and `ls
plan/` shows every task in the order its number really runs.

## How it went

**It is one property, not two rules, and the plan nearly shipped half of it.** The ask was about
`.10`. But "two digits at the front" and "one digit after it" are not two conventions that happen to
sit together — they are the two halves of a single property, *a listing runs in the order the
numbers run*, and either one alone fails to deliver it. Writing them as two rules in the skill and
two branches in the check was fine; what made the property visible was making it a test of its own.
`a_name_that_keeps_the_shape_sorts_the_same_by_bytes_and_by_number` sorts one list of names twice,
once through `PhaseNumber` and once as plain text, and asserts the two agree. That test is the phase;
the two branches of the check are only how it is kept true.

**14.7 predicted the exact file that would break, and then read the danger backwards.** It closed by
saying the byte order of the phase files "goes wrong at `14.10-...`, which does not exist" — and
three tasks later it did exist. What the paragraph got wrong is where the fault would land: it filed
the risk under the sort in `read_tasks`, and the sort was the one thing that stayed correct
throughout, because it parses. Everything that broke was outside this checker entirely. That is the
reusable lesson and it is not about numbering: a rule enforced only where you can enforce it is not
the same as a rule that holds, and the gap between them is invisible from inside the enforcing code.

**The one-line change that was not one line.** The plan named `doc_check.rs:893` as a comment to
restate, on the grounds that its example was now forbidden. Rewriting it turned up a real decision
hiding in it. With the names written correctly, the numeric sort is dead weight — byte order would
now do. Keeping it is deliberate: a name that breaks the rule must still be read into its real place
so it can be reported for what it is, rather than reported as whatever the misordering caused
downstream. The comment says that now, and it says more than the old one did.

**Three amendments in 14.7, not one.** The plan budgeted a single dated block. The file turned out to
make three separate claims that this work changed: the decision itself, a test bullet asserting
`14.9 < 14.10` (now a name the checker rejects, so the assertion had to go rather than be updated),
and the closing section above. Splitting them was right — a block appended under the paragraph it
qualifies is findable, and one block at the top covering three unrelated sentences is not.

**The rename cost nothing, which was not obvious in advance.** Renumbering a closed task looked like
the risky half. It took one `git mv`, two lines inside the file, and two in `ROADMAP.md`, and
`doc-check` named the disagreement at every intermediate step — the deliberately-red run after the
`git mv` reported exactly `says id: 14.9.5, but its name opens with 14.10`. Nothing in the frozen
prose needed touching. Stating the id twice, which 14.7 predicted would make renaming *harder*, is
what made it safe: the checker refuses to let the two drift apart, so the rename could not be half
done.

**A dated consequence.** The two-digit rule at the front holds up to phase 99 and fails at 100, where
`100-...` sorts before `99-...` and the check will fire on it. That is the right behaviour and it is
worth saying it is not an oversight: the check going red is what forces the decision to be taken
rather than discovered in a listing years later. Nothing about the current milestone plan comes close
to phase 100.
