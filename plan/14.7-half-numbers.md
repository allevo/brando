# Phase 14.7 — A half number is read, not cut short

> **Status: implemented**, on 2026-08-14. See [How it went](#how-it-went) at the end, which is where
> the shape it really took is written down. **Everything above that section is the plan as it was
> written**, including the parts the work proved wrong — the prediction next to the outcome is the
> point.
>
> **Its number is a half one because it has no place in the chain.** Every whole-numbered phase reads
> the state the one before it introduced; this one reads no state at all — it touches no crate the
> game runs — so it slots between two of them rather than joining the sequence. It sits after 14.5
> and 14.6 because that is the order the table is read in, not because it depends on either.

**Goal:** `cargo xtask doc-check` reads a half number as a number wherever it reads one, so a half
number can name any kind of work and the check tells the truth about it.
**Depends on:** nothing. Not the map, not migration, not the treasury, not the tables.
**Size:** S — and, unusually, with **no** regeneration attached.

## Why it exists

The tree already uses half numbers for two different kinds of work. One is a decision that has to be
closed before the next whole phase can start — 14.5, 14.6 and 18.5, each naming its `TO_BE_DECIDED`
entry. The other is an ordinary phase that falls between two whole ones and claims nothing about the
state before it: 14.4, which was numbered 22 while it was parked after the map work.
[ROADMAP.md](../ROADMAP.md) already says both are allowed. The script that reads those numbers does
not.

`doc_check.rs` parses a phase number with `chars().take_while(char::is_ascii_digit)`, which stops at
the dot. It does it twice — once on the phase file's name, once on the roadmap's
`Implemented through phase` line — so `14.4-building-kind.md` reads as `14` and
`Implemented through phase 14.4` reads as `14`. **They agree because both are truncated, not because
either is right.** `14`, `14.4` and `14.9` all compare equal, and the one line stating how far the
tree has got can be wrong without anything failing.

That is the whole defect, and it is the kind this project keeps rediscovering: a check that looks
green because it is blind, not because the thing it guards is true. It is the same shape as A5's
absorbing hunger and as the `coverage_equivalence` hole — the guard had a hole in the guard itself.

A third site is softer but the same idea: the `TO_BE_DECIDED` rule tests `slot.contains('.')`, a
substring test rather than a parse, so `M2.x` would satisfy it.

## The shape it will take

One private type in `xtask/src/doc_check.rs`, and three call sites that stop parsing by hand:

```rust
struct PhaseNumber(Vec<u32>);
```

Derived `Ord` on `Vec<u32>` is already component-wise, which is the ordering wanted:
`[14] < [14, 4] < [14, 9] < [14, 10] < [15]`. It gets `leading(&str) -> Option<Self>` — the number a
string *opens* with, so one piece of code reads a file name and a run of prose — plus
`is_fractional()` and a `Display` that prints `14.4`.

- `plan_files_have_a_status` — `highest_implemented` and `claimed` become `Option<PhaseNumber>`.
  `None` orders below every `Some`, so the fold over the files stays one line and an unnumbered
  document can never become the highest.
- `open_decisions_are_scheduled` — `!slot.contains('.')` becomes a parse. Same rule, and the finding
  text does not move.
- The sort of the phase files — byte order puts `14.10-...` before `14.4-...`. This one only fixes
  the order findings print in, but it is the same number being read.

**Out of scope, deliberately.** `doc-check` does not learn to tell a decision slot from a phase, does
not resolve the roadmap's links to files, and does not check that a phase file's `# Phase N —` title
matches its own name. Those are rules about what a row *means*; this phase is about reading the
number. `cited_ids`' three-digit cap is a separate problem and A99 is a long way off.

**The vocabulary does not move.** The words stay *phase* for a whole number and *slot* for a half
one. "Task" is a synonym choice, and [A19](../DECISIONS.md) says a hard word earns its place only
when it is the domain's own.

## The decisions it will produce, none of them taken

**How two half numbers under the same whole phase compare.** Component-wise, as version numbers do,
so `14.10` follows `14.9`; or as a decimal fraction, so `14.10` *is* `14.1` and falls before `14.2`.
The first never runs out of slots between two phases and gives `14.4.1` for free; the second matches
how the number reads aloud. The argument for the first is that the number is an ordering device, not
a quantity — nothing is ever added to or averaged with it.

**Where the number lives.** The file name is the source of truth and the roadmap's line is the claim
checked against it, which is what the existing check already assumes. The alternative — a field in
the phase file's header — is not obviously worse, and would let a file be renamed without breaking
anything.

## What its tests will have to prove

A unit test beside the ones already in `doc_check.rs`:

- `14-births-deaths.md` sorts before `14.4-building-kind.md`, which sorts before `15-migration.md`.
- `14.9` sorts before `14.10`. This is the assertion that fails under decimal reading and is the
  reason the type exists rather than a `f32`.
- `09-invariants-closeout.md` sorts before `10-beyond-m0.md`.
- A half number survives a round trip to text: `14.4-building-kind.md` prints as `14.4`.
- A sentence's full stop is not part of the number: `14. Everything up to` reads as `14`.
- A dated document and `README.md` have no number, and `14..4` is not one either.

## Verification

The one that matters is a **negative** test done by hand, because the defect is that nothing fails:

1. `cargo xtask doc-check` green before anything is touched, so the signal is not lost.
2. Set the roadmap's line to `Implemented through phase 14.9` while the highest implemented file is
   `14.4`, and run `doc-check`. **It passes.** That is the defect, and it has to be seen passing
   before the change to be worth anything.
3. After the change, the same edit fails with
   `says phase 14.9, but the highest phase file marked implemented is 14.4`.
4. `cargo test --workspace`, `cargo clippy --workspace --all-targets -- -D warnings`,
   `cargo fmt --all --check`.
5. `cargo xtask regen-expected --check` **stays green and regenerates nothing.** This phase touches
   no simulation code and no table, so a hash that moves is a bug and not a rebalance. It is the
   rarest kind of phase here: one where the recordings are evidence precisely by not moving.
6. `doc-check` green at the end with this file marked implemented and the roadmap saying
   `Implemented through phase 14.7` — the first time that line is really compared.

## How it went

Implemented on 2026-08-14 in one pass, in `xtask/src/doc_check.rs` and the documents. It produced
[A23](../DECISIONS.md). Six files changed, no recording moved, and `regen-expected --check` was green
before, after, and twice in a row.

### The negative test was the whole phase

Everything else here is small. What the phase is actually worth is the sequence in step 2 and 3 of
its own verification, run in that order: with the roadmap edited to claim phase `14.9` while the
highest implemented file was `14.4`, `doc-check` **passed**. That is the defect, and it is only
visible before the fix — afterwards there is nothing to see, because the fix is that something now
fails. Taking the measurement after the change would have proved that the check works, not that it
had been broken.

Three claims were tried against the finished check, and it now separates all three:

```
14     -> says phase 14, but the highest phase file marked implemented is 14.7
14.5   -> says phase 14.5, but the highest phase file marked implemented is 14.7
14.7   -> all checks pass
```

Before the change, every one of those read as `14` and the first two passed.

### The plan was wrong about the roadmap

It said `ROADMAP.md` would gain a row for this phase. It did not, and should not have: the pattern
14.4 set is that a phase's row is *removed* from the "Next" table when it lands, so a phase planned
and built in one commit would have had its row added and deleted in the same diff. That is a fiction
in the record, and the record is the thing this project protects. What the roadmap gained instead is
the status line, one paragraph in "How to read the numbering", and nothing else.

The half-numbered file, on the other hand, was right, and `plan/README.md`'s section for it went
plural — which is the first sign that "the phase that depends on nothing" was always going to be a
category rather than an exception.

### The sort was prophylactic, not a fix

The plan listed three call sites as though all three were broken. Two were. The third — the byte
order of the phase files — happens to be correct for every file that exists today, because `-`
(0x2D) sorts before `.` (0x2E), so `14-births-deaths.md` already precedes `14.4-building-kind.md`.
It goes wrong at `14.10-...`, which does not exist. It is worth saying plainly: that change fixed
nothing observable and was made because it is the same number being read, not because anything was
failing.

### Two things the plan did not see

**`GLOSSARY.md` was worse than "stale".** The plan noted the row said `A1`–`A19` while A22 existed
and `phase numbers 00`–`18` while 21 did. What it did not notice is *why* it went stale: a range is a
statement of current state, and `CLAUDE.md` already says those belong in `ROADMAP.md` and nowhere
else. The row is now range-free, so it describes the *scheme* and cannot rot again. A document rule
the project already had was being broken in a table nobody re-read.

**`Option` did the ordering for free.** `highest_implemented` became `Option<PhaseNumber>` and the
fold over the files stayed one line — `highest.max(PhaseNumber::leading(name))` — because `None`
already orders below every `Some`. That is also what keeps a dated batch file or `README.md` from
ever becoming the highest: they parse to `None` rather than needing a rule of their own. The plan had
predicted a match arm for "claims a phase while nothing is implemented"; it was written, and it is
still unreachable in this tree.

### What it did not fix, deliberately

`doc-check` still reads the number and not the meaning. It cannot tell a `TO_BE_DECIDED` slot from an
ordinary phase, does not resolve the roadmap's links to the files they name, and does not check that
a phase file's `# Phase N —` title agrees with its own name — the one thing the 22 → 14.4 rename had
to get right by hand, in three places, with nothing watching. That is a real gap and it is now the
obvious next piece of work on this check. It was left out because it is a rule about what a row
*means*, and putting it in the same commit as the parse would have made neither reviewable.
