# Phase 14.10 — Writing a task is a procedure

> See [How it went](#how-it-went) at the end, which is where the shape it really took is written
> down. Everything above that section is the plan as it was written, including the parts the work
> proved wrong — the prediction next to the outcome is the point.

**Goal:** `CLAUDE.md` no longer states how to open or close a task; a skill does, it is loaded when
that job comes up rather than read every session, and its front matter template is checked against
the code that accepts it.
**Depends on:** 14.8, for the front matter the template shows, and 14.7, for the number this task
carries.
**Size:** S — three documents and one check.

## Why now

`CLAUDE.md` answers *how do I work here?* and about a third of it answers something narrower: how to
open a task and how to close one. That third is read in every session, including the ones that never
go near a task, and it is the part a reader carrying it around needs least. It is also the part that
is only ever needed at two particular moments, which is exactly the shape of a thing that should
arrive when it is wanted.

The reason to be careful is one commit old. Phase 14.9 removed the decision register because it was a
second copy of rules that nothing kept in agreement with the first, and a skill restating
`CLAUDE.md`'s task rules would be that same fork, in a file the tools read and a person never opens.
So the content **moves**, and where it cannot move — the front matter template, which is a copy of
what `read_task` accepts whether anyone likes it or not — the agreement becomes a check. That is the
project's own generalisation of the balancing lesson: if you find yourself writing a comment
explaining why two things must agree, write a check instead.

There is already evidence the drift is real and not theoretical. `CLAUDE.md` says `kind` is `phase`
or `open-question`; the code has accepted `constitution` as a third since 14.9 put the constitution
in a task, and nothing noticed for a commit. That sentence is one of the ones leaving.

## What gets built

**A skill, at `.claude/skills/task/SKILL.md`.** It holds three jobs: opening a task, closing one, and
amending one that is already frozen. It states the things the checker cannot see and deliberately
does not restate the things it can — its standing instruction is to run `cargo xtask doc-check` and
read the message, because the checker names the rule it is enforcing and this document would only be
a worse copy of it.

The part worth having is the body shape, because there are **three** of them in the tree and nothing
anywhere says so. A full plan opens with the *nothing in it is implemented* blockquote and runs
`## Why now` → `## What gets built` → `## Out of scope` → `## Tests` → `## Verification`. A sketch
adds a second paragraph to that blockquote and swaps the whole section vocabulary for one that reads
forward — `## The shape it will take`, `## The decisions it will produce, none of them taken`. An
open question has neither blockquote nor goal block, states the problem as its own title, and closes
after `## Why it could be a problem` with **no `## Verification` section at all**, because it is
closed by an answer and not by a command.

That last one contradicts `CLAUDE.md`, which says every task file closes with a Verification section.
All three open questions in the tree are written the other way. The sentence was true when it was
written and stopped being true when open questions arrived; it goes, and the skill says which shape
gets one.

**`CLAUDE.md` loses two sections and gains a row.** *What a task looks like* keeps the doctrine — one
goal, closed by a command giving a yes-or-no answer, one task one commit, and why `kind` and `status`
are two fields — and loses the field-by-field mechanics. *The definition of done for a phase* keeps
the one item that reaches beyond the task file, which is where a decision goes, and hands the seven
to the skill. The document table gains a row, so that *each document answers exactly one question,
and nothing else may answer it* still holds with the answer split: the skill answers *how do I open
and close a task?* in full, and `CLAUDE.md` stops answering it at all.

**A tenth check.** `skill_matches_the_task_header` reads the skill and fails unless its template
names exactly the fields `read_task` requires, and unless the two lines listing the kinds and the
statuses name exactly `TASK_KINDS` and `TASK_STATUSES`. It is the same shape as the frozen-order
check, which already finds a documented line, pulls its backticked list and compares it to a `const`.
A missing skill is a finding, not a silent pass.

## Out of scope

**Two sections stay in `CLAUDE.md`, on purpose.** *Recording a decision* and *regenerating the
recordings without losing the signal* both fire in the middle of work, at a moment nobody would think
to go and load a skill about writing a task. A protocol you have to remember to ask for is a protocol
you skip. They are cross-referenced, not copied.

**The prose of the existing tasks is not touched.** Nineteen of them predate the shapes the skill now
describes and some of them will not match it. They are frozen, they are records of how the shape got
here, and rewriting them to agree with a document written today would destroy exactly the evidence
that makes them worth keeping.

## Tests

1. A template naming the fields the code requires passes; one missing `closed` is a finding that says
   so.
2. A skill listing two kinds where the code allows three is a finding naming `constitution` — the
   drift that is live in `CLAUDE.md` today, used as the fixture.
3. The same for a stale status list.
4. A skill with no header and no lists at all produces three findings, not one: each of the three
   statements is checked on its own, so a file that has rotted completely says so three times.
5. `fenced` reads the first tagged block and not the second, and reports a block opened over nothing
   as missing rather than as empty.
6. The real skill file passes, through the integration test that already runs every check.

## Verification

```sh
cargo xtask regen-expected --check
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
cargo fmt --all --check
cargo xtask doc-check
```

No crate the game runs is touched, so `regen-expected --check` has to be green **and list nothing**,
before and after. If a recording moves in this task, the edit was not the edit it claimed to be.

The check has to be seen red once on purpose — add a field to the template, watch `[skill-template]`
report it, take it out again. A check nobody has watched fail is a check nobody knows works.

And the skill is walked once end to end against this file: opened by following its Opening steps,
closed by following its Closing steps. Any step that cannot be followed as written is a defect in the
skill and gets fixed before the commit. It is the only test of the part `doc-check` cannot see.

**Done when:** `doc-check` is green with the tenth check in it, `CLAUDE.md` states the task mechanics
nowhere, and this file was written by following the skill it adds.

## How it went

**The check had to be split in two before it could be tested, and the plan did not see it coming.**
The design was one function reading the skill and comparing three things, and one function is exactly
what cannot be unit tested here: every case needs a different file on disk. It became
`skill_matches_the_task_header`, which reads and reports a missing file, and `skill_states_the_header`,
which takes the text and does the comparing — which is the shape `read_task` has carried since 14.8,
for the same reason and discovered the same way. The lesson is small and repeatable: a check that
reads a path and judges its contents is two functions, and finding out at the test is finding out
late.

**The drift the check exists to prevent was already there when it was written.** `CLAUDE.md` said
`kind` is `phase` or `open-question`. `constitution` became a third the day before, in 14.9, and the
sentence was not updated — one commit, one stale enumeration, nobody noticed. It was found by reading
rather than by the check, because the check did not exist yet, and the honest reading is that this is
evidence for the check and not a demonstration of it. It is test 2's fixture now, which is the most
that can be salvaged from it.

**One sentence in `CLAUDE.md` turned out to be false rather than merely mechanical.** *Every task file
closes with a Verification section* is true of every phase and of none of the three open questions,
which close with the argument instead. It was written when only phases existed and stopped being true
when open questions arrived — the ordinary way a rule goes stale, and the reason it was worth reading
all three shapes rather than one before writing the skill down. The skill now says which shape gets a
Verification section and which does not, and the false sentence left with the rest of the mechanics.

**Nothing was learned about the sketch shape until it was counted.** The plan assumed two body shapes,
a plan and an open question. There are three: a sketch — `20`, `21` — carries a second blockquote
paragraph and a different section vocabulary that reads forward, `## The shape it will take` and
`## The decisions it will produce, none of them taken`. Nothing anywhere said so, and a skill that had
described two shapes would have quietly pushed the next sketch into the wrong one. Counting is
cheaper than the convention it recovers.

**What the skill deliberately does not contain.** Every rule `doc-check` already enforces is absent
from it, replaced by an instruction to run the checker and read the message. That was the plan and it
survived contact, but it is worth writing down why it is not laziness: the checker's messages name
both sides of every disagreement, and a document restating them would be a worse copy that ages
independently. The one thing that had to be restated — the front matter template, which is a copy of
what `read_task` accepts whether anyone wants it to be or not — is the one thing the tenth check now
guards. That is the whole design: copy nothing you cannot check, check everything you had to copy.

**`.claude` was untracked.** Not ignored — untracked, with only `/target` in `.gitignore`. A skill
that lives there is one machine's convenience and not the repository's rule, so `.gitignore` now
names the two files that really are local, and everything else under that directory is committed with
the tree. It is a two-line change and it is the difference between the skill existing and the skill
counting.
