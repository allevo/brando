# Phase 14.8 — Every task says what it is

> See [How it went](#how-it-went) at the end, which is where the shape it really took is written
> down. Everything above that section is the plan as it was written, including the parts the work
> proved wrong — the prediction next to the outcome is the point.

**Goal:** every document in this directory opens with front matter stating its id, its kind, its
status and its dates, and `doc-check` reads all of it — so a date can no longer be written in three
places and disagree with itself in two of them.
**Depends on:** nothing. It touches no crate the game runs.
**Size:** M.

## Why now

Two of the fields already existed and one of them was already checked. The status header was the only
machine-readable thing a task carried, and it was answering two questions at once: `closed` and
`index` described what the *document* was, while `implemented` and `not yet built` described how far
the *work* had got. A field answering two questions is the shape that produced the disagreements this
project keeps finding.

The rest was convention. Twenty-three of the thirty files carried a `**Goal:** / **Depends on:** /
**Size:**` block that nothing verified, and dates were the worst of it: inside the status line
(`implemented — phase 14, 2026-08-12`), inside a file name (`bug-hunt-2026-08-11.md`), and in the
roadmap's "When" column, with no two files agreeing on which. The project's own rule says that an
agreement between two documents is a check and not a promise to remember.

The trigger was the gap the decisions review left open the day before: fourteen comments in the
sources cite a slot number, and nothing verified those slots existed, because matching bare decimals
in Rust would have reported every version number and every measured millisecond. A task that states
its id in a field is a task a checker can look up. That check is not built here — it belongs with the
work that makes ids the only citation — but it becomes writable here.

## What gets built

**Front matter, five fields, on every task.**

```yaml
---
id: 14.4
kind: phase
status: implemented
opened: 2026-08-13
closed: 2026-08-14
---
```

`kind` is `phase` or `open-question`. `status` is `implemented`, `not-yet-built` or `superseded`.
`closed` is present exactly when the status is one of the last two: work that is not finished cannot
say when it finished, and a date on it would be a guess wearing the clothes of a record.

The id is deliberately stated **twice** — in the field and in the file name — and checked. One copy
would be a source of truth nothing can contradict; two copies that have to agree are a check, and a
check is what this project prefers wherever it can have one.

**Four documents leave the directory.** `README.md`, `bug-hunt-2026-08-11.md`,
`naming-review-2026-08-12.md` and `decisions-review-2026-08-15.md` have no number and are not tasks.
Two of the index's sections were working rules rather than records — one goal per task closed by a
command giving a yes-or-no answer, one task per commit, the verification baseline, and the rule that
an empty crate is surface that invites you to fill it — and those move to `CLAUDE.md`. Its five index
tables answered a question `ROADMAP.md` owns, so they move nowhere. Git keeps all four files.

**A rule about frozen documents that the last review read the other way.** A dead link is a broken
sentence, not a frozen one: when a task points at a file that has been deleted, the link is repointed
and the prose is left exactly as written. The decisions review left `plan/README.md` alone on the
opposite reading. Both readings are defensible and the project cannot hold two, so this one is
written into `CLAUDE.md` where it can be applied rather than re-argued.

## Out of scope

**The decision register.** Removing it is the next task, and a commit that restructures thirty
headers *and* deletes a 1,199-line document is not a commit anyone can read.

**Renaming files.** A task's id is the number its name already opens with. Nothing is renamed, so no
link between two tasks breaks.

**The word *phase*.** It survives as a `kind`, and it stays the word for a numbered piece of work.
What is new is *task*, as the word for a document in this directory — a genuine umbrella over `phase`
and `open-question`, and not a synonym anybody has to learn twice.

## What its tests have to prove

The unit tests beside the ones already in `doc_check.rs`:

- Front matter is read as fields: a well-formed block parses, and a file that does not open with
  `---` is a finding rather than a silently empty header.
- A `closed` date on unfinished work is refused, and a missing one on finished work is too.
- A range in the roadmap's `#` column names every task inside it, so `00–09` covers nine.

And, more valuable than any of them, each new rule is watched failing on the real tree before the
tree is made green.

## Verification

```sh
cargo xtask regen-expected --check      # green before and after: nothing the game runs is touched
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
cargo fmt --all --check
cargo xtask doc-check
```

Both benchmark state hashes have to come back unchanged, measured on the same machine as the ones
taken before the work started. Documents cannot change the simulation, and if one had, the edit was
not the edit it claimed to be.

## How it went

**The status line was carrying more than it looked like.** Stripping it was not one substitution but
three. Most files had it as its own sentence in a blockquote, so the line and the `>` under it came
out together. Three — the open questions — had a blockquote that was *only* the status, and removing
it left a doubled blank line under the H1. Two more had it opening a sentence that carried real
content afterwards (`**Status: implemented**, on 2026-08-14. See [How it went]…`), where a
line-oriented strip would have deleted the rest of the sentence with it. That last shape is why this
was done with a script that refused anything it did not recognise, rather than a regex over
everything.

**The check reported itself twice, and it was right to.** Two of the new doc comments spelled out the
plan directory in prose, and check 1 — the code never cites a document by path — reported both. The
file has carried a `concat!` dodge for exactly this since the check was written; the comments were
reworded instead, because a comment that has to be spelled oddly to survive a check is a comment
about the wrong thing.

**Two amendments were owed to 14.7, and one of them was a prediction coming true.** That phase
considered putting the number in the file's header and wrote the alternative down without taking it:
*"not obviously worse, and would let a file be renamed without breaking anything"*. It arrived here,
and the shape it took is the one the prediction missed — the field did not replace the file name, it
joined it, and the value is in the two having to agree. The same phase also ruled that the vocabulary
would not move and that "task" was a synonym choice; it is in use now, and the amendment says what
changed to earn it. Both are dated blocks under the original sentences, which stand.

**Watching them fail first.** A defect whose symptom is that nothing fails cannot be demonstrated
afterwards, so all eight failure modes were produced deliberately, on the real tree, before the tree
was made green:

| What was broken | What was reported |
|---|---|
| 13's front matter deleted | ``13-house-levels.md: does not open with a `---` front matter block`` |
| 13 given `id: 31` | ``says `id: 31`, but its name opens with 13`` |
| 13's `closed` moved a day | `closed on 2026-08-11, but the roadmap row says 2026-08-10` |
| 13's roadmap row deleted | `says it is implemented, but no row of the roadmap's "Done" table names it` |
| 05's `closed` moved a day | `closed on 2026-08-09, but the roadmap row says 2026-08-08` |
| 14.5 given `kind: phase` | ``row "14.5" calls this an open question, but it says `kind: phase`` ` |
| the roadmap claiming phase 15 | `says phase 15, but the highest implemented task is 14.8` |
| 14.5 marked as finished | ``row "14.5" says the question is open, but this task says `status: superseded`` ` |

The fifth is the one worth having. Task 05 has no row of its own — it is inside the range `00–09` —
and a check that read only single numbers would have passed while comparing nothing, which is exactly
how the rule this one replaces went quiet.

**A revert that took the work with it.** The first attempt at that table used `git checkout --` to
undo each deliberate break. The files had uncommitted work in them, so it restored them to `HEAD`
instead: three tasks lost their new front matter and the roadmap lost every edit, and the later runs
reported the wreckage rather than the rule under test. The demonstrations were redone against copies
kept outside the tree. Worth writing down because the failure looked exactly like a check misfiring.

**What was deliberately not done.** A roadmap row whose `#` is `—` names work that ran without a task
file, and there is nothing to compare its date against. One such row survives. The check skips it and
says so in its own doc comment rather than appearing to cover it: a check that quietly covers less
than it looks like is the failure this file exists to prevent, and it is the failure the review the
day before found in the check it replaced.
