## Why now

The invariants have been written phase by phase, each next to the system it checks. What is needed
is one place where you can read *what the project guarantees*, regardless of how the code is
organised: it is the document a contributor (or an LLM working on the repo) reads to learn what
must not be broken.

## What gets built

### `sim-core/tests/invariants.rs`

One file, one shared generator of command sequences, and one invariant per test — gathering the
ones already written in phases 04–07:

```rust
/// The core's invariants (CLAUDE.md, Testing point 1). Each of these has
/// found or will find a real bug; none of them is to be silenced to make CI pass.
///
/// Shared generator: sequences of arbitrary Commands (invalid ones included)
/// on a 32×32 grid, then N ticks.
```

| Invariant | Origin |
|---|---|
| Population never negative; residents consistent with the houses that exist | D5 |
| Food conserved: `produced == consumed + lost + Σ stock` | phase 07 |
| No overlap between buildings, in both directions tile↔building | phase 04 |
| The treasury adds up: `starting − Σ accepted costs` | phase 04 |
| Incremental coverage ≡ coverage from scratch | phase 06 |
| Network labelling independent of the build order | phase 05 |
| No panic on arbitrary commands, malformed ones included | Testing point 3 |
| Every occupied tile resolves to a live id in the slotmap | phase 04 |

### Fuzzing the commands

`proptest` with 10,000 cases in release already covers point 3 of `CLAUDE.md`. A real `cargo-fuzz`
target (`fuzz/fuzz_targets/commands.rs`) is useful but is not a blocker for M0: if time is short, it
should be noted in this file as debt with the reason, not done half way.

**Decided: debt, not done.** Beyond the property tests there is a deterministic fuzz
(`no_panic_on_ten_thousand_commands`): 10,000 commands generated by a local PRNG with a fixed seed
over 1,000 ticks, checking the structural invariants at every tick. As reproducible as a recording,
and it needs neither a nightly toolchain nor a separate run in CI. To be picked up again when a new
mechanic widens the command space — with `Intent` and the bot (M2/M3) is probably the right moment.

The generator has to produce **bad** commands in significant proportion (coordinates off the map,
`kind`s that do not exist, demolitions of nothing, overlapping areas): a generator that only
produces valid commands checks a tenth of what it looks like it checks.

### A performance tripwire

```sh
cargo xtask bench          # two profiles: 100×100/3,000 res. and 200×200/15,000 res.
```

**It imposes no threshold** — you do not optimise before the profiler. It serves two purposes:
having a starting number recorded here, and noticing if it becomes ten times worse in M1.

#### The starting measurements

`2026-08-08`, Apple M2 Pro, `--release`, 40 repetitions, median:

| Measure | 100×100, 3,000 res. | 200×200, 15,000 res. |
|---|---|---|
| A. empty tick, nothing dirty | 38 µs | 256 µs |
| B. tick, 1 rejected command | 36 µs | 263 µs |
| C. tick, 10,000 rejected commands | 61 µs | 291 µs → **2 ns/command** |
| D. tick, 1 accepted command | 3.3 ms | **19.1 ms** |
| E. tick, 50 accepted commands | 3.5 ms | 20.5 ms → **1.07× D** |

The reference late-game city: 3,750 houses, 1,219 providers, 6,541 road tiles.

#### Two measures added afterwards (`2026-08-09`)

The measures above said *how much* a tick with one command costs, not *where* the time goes. `F` and
`G` answer that question, and were added before optimising step 3.

| Measure | 100×100 | 200×200 |
|---|---|---|
| F. tick, 1 road laid or removed | 3.48 ms | 20.20 ms |
| G. `compute_from_scratch` only (step 3) | 3.43 ms → 14.0 µs/provider | **19.83 ms → 16.3 µs/provider** |

What they say, and why both were needed:

- **`G` settles the question of attribution.** 19.83 ms out of `D`'s 20.05: recomputing the coverage
  **is** the cost of the tick, not one component of it. Everything else — validating the command,
  production over 3,750 houses, emitting the events — sits inside `A`'s 250 µs.
- **The cost is per provider, not per map.** 14.0 µs against 16.3 µs for 4× the tiles: almost flat.
  So the total scales with the number of providers, and what has to go is the cost *inside* the
  per-provider loop.
- **`F` is the case no cache will ever be able to cover.** Laying a road invalidates the topology:
  the network has to be relabelled and every BFS redone. That `F ≈ D` means that even the frequent
  case (building a building) pays the full price of the worst case today. An optimisation that
  brings `D` down and leaves `F` where it is has solved half the problem, and without `F` nobody
  would notice.

#### After the step 3 optimisations (`2026-08-09`)

Same machine, same profiles. Three changes, all of them bit-identical in result — the hashes the
benchmark prints never moved and `regen-expected --check` stayed green at every step.

| Measure | 200×200 before | 200×200 after | |
|---|---|---|---|
| A. empty tick | 256 µs | 248 µs | unchanged, as it should be |
| B. 1 rejected command | 263 µs | 248 µs | unchanged |
| C. 10,000 rejected | 291 µs | 274 µs | unchanged, 2 ns/command |
| D. 1 accepted command | 20.05 ms | **3.35 ms** | **6.0×** |
| E. 50 accepted commands | 20.19 ms | 3.36 ms | 1.00× D |
| F. 1 road | 20.20 ms | 3.42 ms | 5.9× |
| G. `compute_from_scratch` only | 19.83 ms | **3.05 ms** | **6.5×** — 16.3 → 2.5 µs/provider |

The three changes, in order of payoff:

1. `houses_by_tile` from `BTreeMap<TileIdx, Vec<HouseId>>` to an indexed CSR: 19.83 → 12.38 ms.
2. The other two `BTreeMap`s in the per-provider loop — searching for the minimum among the
   candidates (which was not needed: the BFS visits by increasing distance) and the contention
   check, which was being done on *every* candidate and not only on those that fit in the capacity:
   12.38 → 4.85 ms.
3. The BFS's scratch buffer, allocated once per provider instead of once per recomputation:
   4.85 → 3.05 ms.

**The most informative thing is not the 6.5×, it is that the per-provider cost has become flat**:
2517 ns at 100×100 against 2500 at 200×200, where before they were 14.0 and 16.3 µs. The dependence
on the size of the map has disappeared entirely, and all of it was in change 3.

`A` stays at 248 µs and is now the number to watch, because it is paid on **every** tick while `D`
only when the player builds. Inside `A`, the likeliest candidate is `production`, which does one
`coverage.provider(h, Food)` per house — 3,750 lookups per tick in the same `BTreeMap` change 2 took
out of step 3, but on the hot path of every tick. Not measured yet.

**What these numbers say.** They answer the first open question of
[10-beyond-m0.md](10-beyond-m0.md) — *is step 3 really the hot path, or is it the network rebuild?*

1. **Step 3 dominates, by a long way.** A tick that accepts a command costs ~75× an empty tick
   (19.1 ms against 256 µs). It is not the cost of the command: applying 10,000 rejected ones costs
   2 ns each. It is recomputing the coverage, which today is naive — *any* construction invalidates
   all 1,219 providers, and each redoes its own BFS.
2. **The cost is per tick, not per command.** Fifty accepted commands in the same tick cost 1.07×
   a single command. A bot that builds in batches pays the same as one that builds a piece at a
   time — useful information for M2's agent.
3. **The empty tick is already most of a game's time.** 3,650 ticks (10 years) at 256 µs make ~0.9 s
   if the player never builds: acceptable, but it is the number to watch when M1 adds levelling,
   migration and taxes to steps 6 and 7.

   > **Amended by the documentation audit (2026-08-13).** It was the number to watch, and it moved.
   > Phase 14 measured `A` at **3.600 ms** at the reference scale, against the 248 µs recorded above
   > — because A12 makes step 6 invalidate the coverage on essentially every tick, so the empty tick
   > now pays `G` in full. The tables above stay valid as the **end-of-M0** baseline, which is what
   > `xtask/src/bench.rs` compares against; they are no longer a description of what a tick costs
   > today. The current figures are in [A17](../DECISIONS.md).

None of these has to be optimised now. Point 1 already has its safety net: phase 06's
incremental/from-scratch equivalence test is written so that *any* future cleverness about
incrementality is covered without rewriting it.

## Out of scope

Optimisation. Scenarios with objectives, a heuristic bot, an evaluator: those are the scenario test
(`CLAUDE.md`, Testing point 4) and they need `sim-scenario`, which is M1.

## Tests

This phase *is* tests. The criterion is that every row of the table above corresponds to an existing
`#[test]`, and that none is `#[ignore]` without a line of reasoning next to it.

## Verification

```sh
cargo test --workspace
PROPTEST_CASES=10000 cargo test --workspace --release invariants
cargo xtask regen-expected --check
cargo xtask bench
cargo clippy --workspace --all-targets -- -D warnings
cargo fmt --all --check
```

**Done when:** every command is green, the benchmark has a number recorded in this file, and
`CLAUDE.md` says M0 is complete. At that point there is a simulable, deterministic core protected by
replay: the foundation on which M1 can change the balancing without fear.
