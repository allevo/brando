# Phase 16.5 — A seed draws a map, and a person commits it

> See [How it went](#how-it-went) at the end, which is where the shape it really took is written
> down. Everything above that section is the plan as it was written, including the parts the work
> proved wrong — the prediction next to the outcome is the point.

**Goal:** `cargo xtask gen-map --seed <n> --width <n> --height <n>` writes a map that
`load_map_by_id` accepts with no hand editing, and a city built on it reaches a living population.
**Depends on:** 16 — the map file, the ground height, and the four faults its loader refuses.
**Size:** L.

## Why now

Because phase 16 built a format and left exactly one file in it, drawn by hand at 12×8. A format with
one instance is a format nobody has tested, and every map the tree will ever want — a bigger one for
the renderer, a rough one for the benchmark, a handful to balance a scenario across — is currently a
morning of counting characters in a text editor. The generator is the thing that makes the second map
cheap, and the second map is what proves the first one was not a special case.

Because phase 16 already decided where it goes, and the decision is worth honouring rather than
re-taking: the generator is a tool that writes an asset which is then reviewed and committed, and the
core only ever loads files. A generator inside the core would become a frozen part of the determinism
contract — every improvement to it would move every recorded hash, and the rule at the head of every
`.hashes` file, *if this changes without the balancing having changed, a source of non-determinism has
been introduced*, would stop meaning anything at all.

And because it is cheap **now** and expensive later. Phase 20 adds a third block to the map file for
what stands on the ground, and phase 23 wants a fourth terrain for what the soil is worth. Each of
those is one more pass in a pipeline that exists, or one more block in a hand-drawn file that has to
be counted out by hand. Building the pipeline before either of them lands means they inherit it; after,
they each pay for it separately.

It takes a half number because it is tooling. It introduces no state, changes no table, and touches no
step of the tick — which is also what makes its closing test unusually strong, and that is the next
section but one.

## What gets built

### The generator is a crate, and it does nothing but arithmetic

`map-gen`: a library, `sim-core` and dice for dependencies, and **nothing that can touch a disk**.

```rust
/// Draws a map from a seed. Pure: the same arguments give the same map, and
/// nothing is read from or written to a disk.
pub fn draw(seed: u64, width: u16, height: u16, id: &str) -> Result<MapDef, DrawError>;

/// What the map turned out like, for the person deciding whether to keep it.
pub fn report(def: &MapDef, data: &DataSet) -> Report;
```

A crate and not a module inside `xtask`, for three reasons and against one real cost. `xtask` is the
headless runner — *single games, batches, regenerating the recordings*, as its own module doc says —
and drawing a map is none of those. Nothing can depend on a binary, so the day a scenario or a client
wants a map drawn, the code has to move anyway. And a crate's dependency list is a statement that can
be read: this one names no crate that does I/O, and that absence is the whole of what it promises.

The cost is that a crate is a door. A module inside `xtask` is *structurally* incapable of being loaded
while a game is running; a crate is not, and what is behind that door is the thing the phase before this
one forbade. So the rule is written as a check rather than as a sentence to remember — see below.

**On the name.** `gen` is an abbreviation, which the naming rule leans against, and it earns its place
here by being the word the command line already uses: `regen-expected` exists, `gen-map` is the command
this crate is the body of, and a crate named after its command is easier to find than one named after a
principle. It is deliberately **not** `sim-map`: the `sim-` prefix reads as *part of the simulation*,
which is precisely the thing this code is not, and a prefix that says the opposite of the truth is worse
than an abbreviation.

Two modules to start: the pipeline, and the noise. A third earns its own file when it grows into one.

### The map's alphabet gets one owner, in both directions

`sim-data` knows that `.` is plain, `~` is water, `#` is rock, and that a ground height is a base-32
digit. It knows it in one direction only — reading — because until now nothing wrote a map that was not
a person with a keyboard. A generator that spells those alphabets out a second time is a second copy of
a rule that nothing keeps in agreement with the first, which is the fork this repository removed an
entire decisions register to stop making. So the inverse goes beside the original, in `map.rs`:

```rust
/// Parses map text into a validated `MapDef`.
///
/// Extracted from the middle of `load_map_by_id`, which now calls it: reading
/// a file and reading the text in it are two jobs, and only the second one is
/// wanted by something that has just produced the text itself.
pub fn parse_map(text: &str) -> Result<MapDef, MapLoadError>;

/// Renders a validated map back into the text `parse_map` reads, legend
/// comments and all: a character table is documented where it is defined.
pub fn render_map(def: &MapDef) -> String;

/// Renders `def` and writes it to `path`, refusing to write anything
/// `load_map_by_id` would not accept.
///
/// The check is on the rendered **text**, never on `def`: a fault in the
/// alphabet or in the length of a row exists only once the text exists, and a
/// writer that checked the struct it started from would be marking its own
/// homework. Nothing reaches the disk until the real loader has accepted it.
/// `note` is prepended as comment lines — the caller says where the map came
/// from, this function says what the format is.
pub fn save_map(def: &MapDef, note: &str, path: &Path) -> Result<(), MapSaveError>;
```

`save_map` is the same shape as `Recording::save`, and for the same reason: the crate that owns a format
owns writing it. Putting the refusal here rather than in the tool means the guarantee is not the tool's
good behaviour — it belongs to the format, and every writer after this one inherits it.

### The front door stays in `xtask` and stays thin

```
gen-map --seed <n> --width <n> --height <n> --id <name> [--out <path>] [--print]
```

It parses the flags with the helpers already in `main.rs`, loads the tables, calls `draw`, prints
`report`, and calls `save_map`. It gains no RON dependency of its own, because `parse_map` above means
it never needs one. Every command in this tree goes through `cargo xtask`, and a second command surface
for one tool would be a worse trade than the one line of dispatch it saves.

**Width and height are inputs, and the size of the map that gets committed is not decided here.** It is
decided after watching one play, the way `max_build_slope` was set against a playtest rather than in the
abstract. A plan that fixed it now would be fixing it from a picture in somebody's head.

### The passes, and what each one is for

Six functions, in this order, and the order carries meaning in two places worth naming.

1. **Relief.** Layers of noise over the map, in fixed point.
2. **The border falls away**, so a map ends in sea rather than in land sliced off at the frame.
3. **Quantise to steps**, `0..=31`, against the range the noise has *by construction* and not against
   the range this particular seed happened to reach. Stretching each map to fill the field would make a
   gentle seed come out as jagged as a violent one, and would make the sea level mean a different height
   on every map — which is the same failure as a threshold that is not comparable between two runs.
4. **Classify.** Water below the sea level; rock above the rock height, or where the step to the
   steepest neighbour is at least the rock step; plain otherwise.
5. **The water flattens to height zero.** *After* classification, which is the first place the order
   matters: dropping the sea first would put a large step between every shore tile and the water beside
   it, and the classification would read that step as a cliff and turn the whole coastline to rock.
6. **One walkable region survives.** Flood-fill, keep the largest, drown every walkable tile outside it.

**The sixth is the gate, and it is not a nicety.** The loader refuses a map whose walkable tiles are in
more than one piece, because until bridges exist a river across the map silently strands half of it. A
generator that can emit such a map is a generator that emits files the game will not load, so the repair
is not a polish pass at the end — it is the condition on which the whole tool is useful at all. Largest
by tile count, ties broken by the lowest tile index in the region: an unstated tie-break is a source of
non-determinism, and the whole point of writing one down is that nobody has to wonder later.

The flood fill lives in the generator and not in `Grid`. `walkable_regions` returns the sizes of the
regions and not which tile is in which, and widening a signature in the core for a tool's convenience is
exactly how this phase would lose the right to claim it changed nothing inside the simulation.

`DrawError` carries two refusals and no more: a size the grid will not take, and a seed whose map has no
walkable tile left at all.

### The noise, and why not simplex

Value noise: a lattice every so many tiles, eased between the four corners around each tile, several
layers added together — **each layer half the strength and twice the detail of the one before**. The big
layers make the landforms and the small ones the roughness.

Those two ratios are written into the loop and given no names. That is deliberate and it is the same
argument that made the calendar a constant instead of a table row: nobody tunes what a layer *is*. Two
knobs that no one would ever turn are two knobs to document, validate and regret, and refusing them is
also what keeps two hard words out of the vocabulary — the strength ratio and the detail ratio have
standard names in the literature and neither of them would survive the naming rule.

Fixed point throughout, because floats are denied workspace-wide and because the output is five bits
wide: there is nothing a float would buy here that an integer does not already have, and integers have
the additional property that two machines cannot disagree about them.

**Simplex noise is refused, and it is the tempting one.** It needs a table of gradients and a skew factor
that is not a ratio of small integers, so it costs either the float ban or a constant fudged until it
looks close enough — and its one genuine advantage, that it leaves no pattern lined up with the axes, is
invisible at five bits of relief seen through a water threshold and a rock threshold. It would be a real
improvement on a map with two hundred and fifty-six levels of height. This is not that map.

**Nothing here is invented that the tree already has.** Each layer's lattice is filled from a `Pcg64`
seeded by a blake3 of the seed, the field's name and the layer — which is exactly the device the core
already uses to keep its four streams apart, and the same generator the benchmark's ragged street map
already draws from. No hand-rolled mixing constants anywhere.

**The field's name is an argument to the noise, and that is not machinery.** A hash of coordinates takes
a name the way it takes an x and a y; it costs one more argument to a function that exists, not a type
and not an enum. What it buys is that a second field added later — outcrops of rock scattered on the
plain, trees, soil — cannot shift the one drawn first. The core's `RngKind` is deliberately **not**
reused for it: that enum's declaration order is frozen and enters every recorded hash, so a fifth entry
for a tool that never ticks would move every recording in the tree to buy nothing.

### Nothing the simulation loads may depend on the generator

`ARCHITECTURE.md` already carries a sentence of this shape — *if `game-bevy` ever appears among another
crate's dependencies, that is an architectural mistake* — and it has never been anything but a sentence.
This phase makes its own version a check: `doc-check` reads the workspace manifests and fails if
`sim-core`, `sim-data` or `sim-replay` names `map-gen` among its dependencies. `xtask` may, and does.

It is the answer to the one cost of making the generator a crate, and it is this repository's own lesson
applied without modification: *a relation that has to hold is a check, not a comment.* A rule that only
lives in prose is a rule somebody breaks on a Tuesday; a rule the build refuses is one nobody can.

**One trap with it, small and silent.** `doc_check.rs` walks a hardcoded list of crate directories. A new
crate missing from that list does not fail anything — it simply escapes every source check the tool
performs, quietly and for ever. Adding the crate to that list belongs in the same commit that creates it.

### What the report says, and what it deliberately does not say

The share of each terrain, the range of heights, how many walkable regions there were before the repair
and how many tiles it drowned — and then the number that actually decides anything:

> for each distinct footprint in the buildings table, how many positions on this map that building could
> stand in: buildable ground, and a slope within `max_build_slope`.

A map that is 60% land and beautiful in a diff is worthless if no farm fits on it, and the terrain shares
cannot tell you that — they are the statistic that is easy to compute rather than the one that answers
the question. The figure above is read from the real tables, so the tool and the game cannot come to
different conclusions about what is placeable, which is the same discipline that keeps the treasury
invariant an exact equality.

The report is printed for a person to read. **It never changes what is generated.** A tool that quietly
regenerates until its own statistics look good is a tool whose seed no longer means anything, and the
seed meaning something is the only reason to have one.

### The header comment, and the promise it deliberately does not make

The written file opens with the command that drew it, and with the sentence that stops that line being
read as a contract:

```ron
// Drawn by `cargo xtask gen-map --seed 7 --width 48 --height 32 --id <name>`,
// then read by eye and committed. That line records how this file was first
// drawn; it is not a promise that the same command would draw it again. The
// generator is a tool and is free to improve, where this file is an asset the
// recordings hash — which is the whole reason the generator is not core code.
```

**This is the decision in the phase most likely to be quietly undone later, so it is stated here at
length.** The obvious next thought, once there is a generator and committed maps, is a
`gen-map --check` that redraws every committed map and compares — the shape `regen-expected` already
has, and it looks like rigour. It is the opposite. It would make the generator's output a frozen
contract, so that improving the noise would fail a check, and the way to make the check pass would be to
redraw the maps, and redrawing the maps moves every recording that names one. The generator would be
back inside the determinism contract by the back door, and phase 16 put it outside on purpose.

The same argument refuses generating at play time from the recording's header. The recording names a map
and carries its hash so that an edited map fails immediately and for the right reason; a recording that
named a seed instead would be trusting the generator to be identical for ever.

Determinism is still tested, and the test says what it means: same seed, same size, same binary, same
map. Across versions of the tool, nothing is promised, and nothing needs to be.

### The words

`layer` for one round of noise. `ease` for the curve between two lattice corners. The sea level, the rock
height, and — separately — **the step to the steepest neighbour**, which is emphatically *not* called a
slope: `slope` already means the range of ground heights across the tiles a building sits on, and a
second meaning for a word that has one is the failure the glossary entry for `capacity` exists to guard
against.

`noise` is the one hard word that earns its place, being the domain's own, and it goes in the glossary
when the phase closes. The constants that shape a map are the generator's own, not table rows: what binds
a number to `sim-data` is the simulation reading it, and the simulation reads the file the tool wrote,
never the tool. The one number here that *is* a table number, `max_build_slope`, arrives through the
dataset and is never restated.

## Out of scope

**Rivers.** Water is where the ground is below the sea level, and nowhere else. A river is a walk downhill
from a high point to the sea, and it is the one feature that reliably cuts a map in two — so it arrives
with a ford drawn beside it, which is a second mechanism, or after bridges, which is phase 21. Either way
it is not the first thing the tool learns to draw. The hand-drawn `river-valley` keeps the name in the
meantime.

**Erosion**, which is the same class of thing: a large improvement to how a map looks, resting on a
pipeline that has to exist first.

**A field of its own for rock**, so outcrops appear on the plain rather than only above a height. Named
here rather than left out, because the noise takes the field's name for exactly this and the temptation
will be to do it in the same afternoon — which would give one tool two reasons to change in one commit.

**Trees and what stands on the ground.** Phase 20 adds the block to the map file; the pass that fills it
lands with the block, not before it.

**What the soil is worth.** Phase 23's business, and it wants a fourth terrain that does not exist yet.

**Roads, buildings, a starting city.** A map is ground. What is built on it is the player's, and on the
scenarios the AI plays it is the scenario's.

**Replacing `river-valley`.** It stays exactly as it is. It is the fixture the loader's fault tests are
written against, and a hand-drawn map is the only kind you can write a *specific* fault into — a
generated one that happens to be broken this week is a test that passes for the wrong reason next week.

**A check that redraws the committed maps**, and **a map generated from a seed at play time**, both for
the reason argued above.

## Tests

1. ***The test that defines the phase.*** Across a sweep of seeds and sizes, every map `draw` produces
   survives `render_map` → `parse_map` → `validate_map`. Through the rendered text and not the arrays it
   came from: a generated map the game refuses to load is the entire failure mode, and the loader is the
   only honest judge of it.
2. **The round trip, where both halves live.** Rendering the committed hand-drawn map and parsing it back
   gives an equal map with an equal hash — comparing maps and not bytes, since the comments and the
   spacing belong to the renderer. Plus a property test over drawn maps. This test sits in `sim-data`
   between the two functions it holds together, which is the point of putting them in the same file.
3. **The writer writes nothing the loader would refuse.** Hand `save_map` a deliberately severed map: it
   returns an error and leaves no file behind. The no-partial-mutation discipline, applied to a disk.
4. **One walkable region, always.** For seeds that produce several before the repair, exactly one after;
   and the repair only ever drowns land, never creates it.
5. **Every ground height is in range**, as a property over seeds and sizes. Guaranteed by construction,
   which is exactly why it is worth pinning: the construction is what a later change would alter.
6. **A seed is the whole of what makes a map.** The same seed and size twice give an equal map; two seeds
   do not. The second half needs a realistic size to mean anything — on a one-tile map every seed agrees.
7. **The corners do not panic.** 1×1, and both extremes of the largest side the grid allows. A size the
   grid refuses comes back as a clean error naming the limit; a seed that leaves no walkable tile comes
   back as the other error, not as an empty map.
8. **Water sits at height zero** on every map drawn, pinned so that the pass which puts it there cannot
   quietly be dropped by someone reordering the pipeline.
9. **Somewhere to put the largest building.** Every map in the sweep has at least one position where the
   biggest footprint in the buildings table fits within `max_build_slope` — read from the real tables, so
   that a change to either one is caught by the other.
10. **Nothing the simulation loads depends on the generator.** The new check, run from `cargo test` with
    the others.
11. **A drawn map plays.** A scenario on the committed map reaches a living population across 900 ticks
    with no command rejected, watched the way `river-valley` was: the population and the fraction of
    residents covered, side by side. A map that cannot be built on is a seed to throw away, not a rule to
    loosen.
12. ***The test that closes the phase.*** `regen-expected --check` is green **before and after**. This
    phase adds no core code, no table value and no step to the tick, so **nothing the simulation hashes
    may move at all**. It is this phase's equivalent of the previous one's identical dumps, and unlike
    that one it is a plain equality rather than a comparison by eye.

**The prediction this phase has to check against reality**, stated so that being wrong about it is
visible: test 12 passes untouched, and the first seeds drawn come out *too rough to build on* rather than
too flat. The second half is a guess about the noise rather than about the code, and if the first maps
are instead featureless, the layer strengths are wrong in the opposite direction from expected and that
is worth knowing before tuning anything.

## Verification

The protocol needs the *before*, and here the before and the after have to be the **same** — which is
the unusual thing about this phase and the reason its verification is short.

```sh
# Before touching anything. If this is not already green, the tree is dirty for
# other reasons and the one signal this phase depends on is already lost.
cargo xtask regen-expected --check
```

```sh
# After.
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
cargo fmt --all --check
cargo xtask gen-map --seed <n> --width <n> --height <n> --id <name> --print
cargo xtask run --scenario <name> --ticks 900 --dump-every 30
cargo xtask regen-expected --check   # still green: nothing may have moved
cargo xtask doc-check
```

Draw several seeds and sizes before choosing one, and choose on the report rather than on the picture.
The number to read is how many positions the largest building has; the terrain shares are decoration.
`bench` is not re-run: nothing in this phase is reachable from `step()` at all, which is the same fact
test 12 asserts and there is no point asserting it twice by two different methods.

**Done when:** the tool writes a map with no hand editing that `load_map_by_id` accepts, a city built on
it reaches a living population with no command rejected, the new check proves that no crate the
simulation loads depends on the generator, and `regen-expected --check` is green both before and after —
the last of which is what proves that a generator living outside the core changed nothing inside it.

## How it went

**The prediction was right, and it was right for a reason the plan did not have.** The first seeds came
out too rough to build on, exactly as predicted — but "too rough" turned out to name two separate
faults, neither of them a matter of tuning a threshold, and both of them visible only in the picture.
The report could not see either: it said 388 places for a farm on the first map drawn, which is
plenty, while the map itself was ground speckled with rock and ringed by a wall of it. That is worth
recording against the plan's own instruction to *choose on the report rather than on the picture*. The
instruction is right for choosing between seeds and wrong for judging whether the tool works at all,
and the difference is that the report answers a question you already know to ask.

**The first fault: the finest layer of noise was not noise.** The plan has the layers running until the
corners are one tile apart, and a layer whose corners are one tile apart gives every tile a value drawn
without reference to the one beside it — which is static, not landscape. The very next pass turns a
large step between neighbours into rock, so it read that static exactly as written. The layers now stop
while the corners are still at least two tiles apart. Rock fell from 24% to 16% and the farm's places
rose from 388 to 604, on the same seed, with no threshold touched.

**The second fault: the step into the sea was being counted as a cliff.** The ground goes on falling
under the water, so the drop from a shore tile to the sea beside it is large on almost every map, and
every map came out ringed with cliffs. A beach is not a cliff: nobody climbs the drop into the sea, so
it is not a step, and the measurement now skips neighbours below the sea level. This is the change the
plan came closest to predicting and still missed — it named the *order* of classifying and flattening
as the subtle thing, and got that right, but the sea's own depth was never in view.

**A third change was made for a reason and then found to be nearly irrelevant, which is worth recording
as such.** The border falloff now runs down the noise's own ease curve rather than down a straight
line, so it is flat where it meets the land. The argument is sound and the change is one line, but the
rim it was meant to remove was mostly the second fault above, and what remains after both fixes is
genuine terrain: on this map the shore is rock where the interior behind it is high and plain where it
is low, which is what a coast does. Widening `BORDER_MARGIN` instead was tried at 8 and at 10 and
rejected on the evidence — the falloff is multiplicative, so a wider margin does not gentle the shore
so much as eat the island.

**`draw` returns a `Drawn` and not a bare `MapDef`.** The plan's report was to say how many walkable
regions there were before the repair and how many tiles it drowned, and neither survives into a
finished map — after the repair there is always exactly one region, so a `MapDef` alone cannot answer.
They are facts about the drawing, so the drawing returns them.

**`parse_map` returns a `MapParseError` and not a `MapLoadError`.** The plan's signature could not have
compiled: `MapLoadError::Ron` carried the path of the file, and a function reading text has none.
Splitting the path off is what lets the writer refuse with the *same type* the loader refuses with,
which is a better outcome than the plan asked for — "what `load_map_by_id` would not accept" is now one
type rather than a promise that two of them agree.

**Two names in the plan's own prose did not survive its own naming rule.** `lattice` and `quantise` are
neither elementary nor in `GLOSSARY.md`, and neither reached the code: the corners a tile is eased
between are a `corner_spacing`, and the pass is `to_steps`. `noise`, `layer` and `ease` went into the
glossary as the plan said, and `slope`'s entry gained a sentence saying in as many words that the step
to the steepest neighbour is not one.

**The new check was verified by breaking the tree on purpose**, which is the only way to know a check
works: `map-gen` was added to `sim-data`'s manifest, `doc-check` failed naming the file and the rule,
and the manifest was put back. A check nobody has watched fail is a check nobody has tested.

**The closing test held.** `regen-expected --check` was green before the first line was written and
green after the last, with nothing regenerated — which is what this phase claimed, and the reason it
took a half number. The committed map is `open-plain`, seed 19 at 48×32, chosen from six drawn: every
one of them had places to spare for the largest building, so the number the plan nominated as decisive
did not in the end decide anything and the picture broke the tie. Fifteen houses on it reach 118
residents over 900 ticks with no command rejected, and one of the six farms sits on a slope of two —
ground a seed drew is not flat, and a scenario that only ever built on the flat parts of it would have
proved less than the plan asked for.
