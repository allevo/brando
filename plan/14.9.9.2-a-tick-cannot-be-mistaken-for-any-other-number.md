# Phase 14.9.9.2 — A tick cannot be mistaken for any other number

> See [How it went](#how-it-went) at the end, which is where the shape it really took is written
> down. Everything above that section is the plan as it was written, including the parts the work
> proved wrong — the prediction next to the outcome is the point.

**Goal:** the simulation's current tick is a `Tick`, not a bare `u32`, so it can no longer be added
to a building-kind id or compared against a residents count by accident — the same guarantee
`BuildingKindId`/`TileIndex`/`Level` (`sim-core/src/ids.rs`) and `Milli`/`Coins`
(`sim-core/src/units.rs`) already give their own values.
**Depends on:** nothing. The tick field has existed since phase 04, unchanged in type since then; this
reads no state a later phase introduced.
**Size:** M — one new type, and every call site the compiler names once the field's type changes.

## Why now

`ids.rs`'s own header says the rule out loud: *"a bare `usize` never appears in a public signature."*
`units.rs` gives the same treatment to a quantity: `Milli`/`Coins` cannot be added to each other by
accident, and their comments say why an operator would be the wrong tool. The one value threaded
through just as many signatures — `World::tick`, `Checkpoint::tick`, `Recording::commands_at_tick`,
`sim-replay::checkpoints`'s `until`, the CLI's `--ticks` — never got the same treatment, and it is
exactly the class of value the newtype pattern exists for: today nothing stops a tick from being
compared against `ticks_per_month` (a duration, not a moment) or handed to a function expecting a
`BuildingKindId`, because both are spelled `u32`.

## What gets built

`Tick`, in `sim-core/src/tick.rs` (the module already responsible for the tick per `ARCHITECTURE.md`'s
module table), wrapping a `u32`:

- `Clone, Copy, PartialEq, Eq, PartialOrd, Ord, Hash, Debug`, and a hand-written `Display` that prints
  the bare number — no `Serialize`/`Deserialize`, the same choice `Level`/`DifficultyId` made, so nothing
  can write the newtype straight into a save file by accident.
- `ZERO`, `new`, `get` — the same constructor/accessor shape as `BuildingKindId`/`TileIndex`/`Coins`.
- `next()` — the one arithmetic operation the core itself performs on a tick (advancing `step()`),
  saturating like today's `world.tick.saturating_add(1)`.
- `is_multiple_of(n: u32)` — what `Rules::is_month_boundary` needs, named instead of exposed as `Rem`.

No `Add`/`Sub`, for the reason `Milli`/`Coins` already give: the operator invites raw arithmetic at
the call site where a dedicated method should say what the arithmetic means.

**Instant vs. duration.** `Tick` replaces every place a bare `u32` names a *point* in simulated time:
`World::tick`, `Checkpoint::tick`, `replay`/`advance`/`checkpoints`'s `until`,
`Recording::last_tick`/`commands_at_tick`, `Scenario::commands`/`commands_at_tick`. A *duration or
stride* — `ticks_per_month`, `ticks_per_year()`, `CHECKPOINT_EVERY`, `checkpoints`'s `every`, the CLI's
`--ticks`/`--dump-every` — stays a plain `u32`; it isn't a moment, forcing it into `Tick` only moves
the arithmetic problem sideways. `sim-data` is untouched: `RawRules`/`Rules::ticks_per_month` are both
durations.

**The one place a bare `u32` legitimately survives.** `Recording` (`sim-replay/src/recording.rs`)
derives `Serialize`/`Deserialize` and its `commands: Vec<(u32, Command)>` field is written straight
into the `.ron` files; since `Tick` has no serde impl, that field's type does not change — it *is* the
wire format. Only `Recording`'s methods become `Tick`-typed, converting via `.get()` internally.
`xtask/src/expected.rs::record()` is the one place that crosses this boundary explicitly, converting
`Scenario::commands: Vec<(Tick, Command)>` back to the wire shape.

Touches, concretely: `sim-core/src/{tick,world,data,lib}.rs`; `sim-replay/src/{replay,hash,recording,expected}.rs`;
`xtask/src/{scenario,expected,main}.rs`; the tests in `sim-core/tests/*.rs` and
`sim-replay/tests/expected.rs` that compare or combine `w.tick()` with a bare integer — the field's
type change is what finds every one of them, since they stop compiling.

## Out of scope

- `sim-data` — untouched; nothing there names an instant.
- `xtask/src/bench.rs`'s `ticks`/`ticks_a` fields — benchmark iteration counts, not values flowing
  through a `Tick`-typed API.
- `Add`/`Sub`/`Rem` on `Tick`, and `Serialize`/`Deserialize` on `Tick` — deliberately left off; see
  above.
- Any change to the state hash's byte layout, the `.ron`/`.hashes` formats, or the ten-step tick's
  order. This is a type-level refactor with no behaviour change.

## Tests

- Unit tests beside `Tick`, mirroring `ids.rs`'s style: `next()` advances by one and saturates at
  `u32::MAX`; `is_multiple_of` agrees with the values `is_month_boundary` already relies on;
  `Display` prints the bare number (`Tick::new(42).to_string() == "42"`) — load-bearing for the
  `.hashes` format, not just a style check.
- The full existing suite continues to pass **unmodified in behaviour**: every fix at every call site
  is a signature-level type change, never a logic change.
- `cargo xtask regen-expected --check` green before touching any code, and green again after — zero
  recordings regenerated. That is the actual proof this changed no behaviour: the state hash is
  computed from `w.tick().get()`, the same `u32` value hashed before.

## Verification

1. `cargo xtask regen-expected --check` — green before starting.
2. `cargo build --workspace` and `cargo test --workspace` green.
3. `cargo clippy --workspace --all-targets -- -D warnings` and `cargo fmt --all --check` clean.
4. `cargo xtask regen-expected --check` — green again, reporting nothing to regenerate.
5. `cargo xtask doc-check` green.

**Done when:** no `u32` (or `usize`) representing a tick instant appears in a public signature
anywhere in the workspace outside `Recording::commands`'s own field declaration, and
`regen-expected --check` is green both before and after.

## How it went

**Built exactly as designed.** `Tick` wraps a `u32` with `Clone, Copy, PartialEq, Eq, PartialOrd,
Ord, Hash, Debug` and a hand-written `Display`, no `Serialize`/`Deserialize`, no `Add`/`Sub` — `ZERO`,
`new`, `get`, `next`, `is_multiple_of` turned out to be exactly the operations every call site needed
and no more. The instant/duration split held everywhere it was predicted to: `sim-data` was not
touched at all, and `ticks_per_month`/`ticks_per_year`/`CHECKPOINT_EVERY`/the CLI's `--ticks`/
`--dump-every` all stayed plain `u32`.

**Fewer test files needed touching than the plan hedged for.** The plan listed
`sim-core/tests/{levels,demographics,satisfaction,invariants,commands,coverage,food,roads}.rs` as
"representative, not exhaustive." In practice only three needed a real edit: `commands.rs` (one `+ 1`
became `.next()`), `invariants.rs` (one `TICKS as u32` comparison became `.get()`), and `levels.rs`
(six sites — the only file with genuine tick arithmetic: `run_to`'s parameter and `review_after`'s
return type became `Tick`, and every `+`/`/`/`%` against `w.tick()` went through `.get()` then
`Tick::new`). `demographics.rs`, `satisfaction.rs`, `coverage.rs`, `food.rs` and `roads.rs` compiled
unchanged — their tick usage went entirely through the `tick()` step helper or `{w.tick()}` inside a
format string, neither of which the field's type change disturbs. This is worth recording because it
confirms the plan's central mechanism claim rather than merely asserting it: the compiler, not a
grep, is what found every real site, and it found strictly fewer than the conservative file list
suggested.

**The dedicated method paid for itself outside the one call site that motivated it.** `is_multiple_of`
was written for `Rules::is_month_boundary`, but `levels.rs`'s
`the_level_only_changes_at_a_review` test had its own `at % month == 0` check, which became
`at.is_multiple_of(month)` — a straight improvement in readability the plan did not call out in
advance, just a consequence of the method existing.

**One boundary comment added beyond the plan's file list.** `Recording::commands`'s doc comment
(`sim-replay/src/recording.rs`) gained a paragraph explaining why it stays `Vec<(u32, Command)>` and
naming `last_tick`/`commands_at_tick` as the only things that should read it — the plan's design
section argued for this at the prose level but its file-by-file list did not itemise a comment edit.

**The central prediction held exactly.** `cargo xtask regen-expected --check` was green before any
code changed and green again after, reporting nothing to regenerate: the state hash's bytes come from
`w.tick().get().to_le_bytes()`, the same `u32` value hashed before, so every recorded replay is
byte-for-byte what it was. `cargo test --workspace`, `cargo clippy --workspace --all-targets -- -D
warnings`, `cargo fmt --all --check` (for every file this phase touched — a pre-existing, unrelated
formatting drift in `sim-core/src/coverage.rs` predates this branch and was left alone) and
`cargo xtask doc-check` are all green.

`ARCHITECTURE.md`, `RULES.md` and `GLOSSARY.md` are unaffected, consciously: the `tick` field already
existed and only its type changed, no step moved, no field was added to `World`, no crate arrived, no
new domain word was coined. `ROADMAP.md` gained this row when the task opened and now moves to
`## Done` with today's date.
