# Phase 14.9.9.3 — Nobody tunes what a month is

> See [How it went](#how-it-went) at the end, which is where the shape it really took is written
> down. Everything above that section is the plan as it was written, including the parts the work
> proved wrong — the prediction next to the outcome is the point.

**Goal:** `ticks_per_month` and `months_per_year` stop being fields `Rules` loads from `rules.ron`
and become `Calendar`, a pair of hardcoded constants in `sim-core` — closed by `cargo xtask doc-check`
and `cargo xtask regen-expected --check` both green, and no `.rs`/`.ron` file in the tree naming
either field.
**Depends on:** 14.9.9.2, whose `Tick` newtype `Calendar::is_month_boundary` is built on.
**Size:** M — one new type, and every call site the removal of two `Rules` fields finds, across
`sim-core`, `sim-data` and both crates' tests.

## Why now

`D6` states plainly: *"Everything numeric... lives in RON tables loaded and validated at startup."*
`ticks_per_month`/`months_per_year` are numeric, so on the letter of it they belong in `rules.ron`
like any other field `Rules` carries — a cost, a range, a threshold. The nearest precedent,
`plan/14.9.7-a-terrain-says-what-it-allows.md`, hardcoded `terrain.ron`'s `buildable`/`walkable`
columns and stayed *inside* `D6`'s boundary specifically because those were booleans; its own closing
note said so out loud: *"D6 was not amended: it binds everything numeric, these are booleans."* That
same note named `road_cost` as the thing that would cross the line if it were ever hardcoded, because
it is a number. This phase hardcodes a number. It is not the same move as 14.9.7's, and does not get
to lean on 14.9.7's reasoning — it needs its own argument, which is this:

**A number belongs in a table when a designer might reasonably turn its knob.** Every other field
`Rules` carries is exactly that: `starting_treasury` sets the difficulty of the opening, a house
level's thresholds set the pace of the climb, a demographic rate sets how fast the city grows. Turning
any of them changes what the game asks of the player, and `D6` exists so that changing them never
needs a recompile — a designer edits `rules.ron`, not `sim-core`.

`ticks_per_month` and `months_per_year` are not that. Nobody tunes what a month **is**. A month of
forty-five ticks is not a harder or easier game — every threshold in `rules.ron` is written and
balanced *in units of ticks and months*, so changing the length of one silently rescales every other
number in the table without anybody touching them, which is not tuning, it is breaking the units the
rest of the file is written in. Nothing in this project's plans — including `plan/18-sim-scenario.md`,
which reads objectives in months and years, and `D6` itself, which anticipates a *second civilisation*
with different spatial rules but never a different calendar — ever proposes retuning it. A number with
no designer behind its knob is not balancing data; it is closer to `Terrain`'s frozen declaration
order or `CHECKPOINT_EVERY`, both already hardcoded, both already load-bearing for every recording
without living in a table.

This is a genuine exception, not a reinterpretation of `D6`'s existing words the way 14.9.7's booleans
were, so `D6` gets its first dated amendment rather than a silent pass. The amendment is narrow: these
two constants, and the argument above, not a general licence to hardcode a number that looks
inconvenient in a table.

## What gets built

`Calendar` in `sim-core/src/tick.rs`, alongside `Tick` (which already exists to represent points in
simulated time; `Calendar::is_month_boundary` replaces the one thing `Tick::is_multiple_of` was built
for in 14.9.9.2):

```rust
pub struct Calendar;

impl Calendar {
    pub const TICKS_PER_MONTH: u32 = 30;
    pub const MONTHS_PER_YEAR: u32 = 12;
    pub const TICKS_PER_YEAR: u32 = Self::TICKS_PER_MONTH * Self::MONTHS_PER_YEAR;

    pub const fn is_month_boundary(tick: Tick) -> bool {
        tick.is_multiple_of(Self::TICKS_PER_MONTH)
    }
}
```

Removed: `Rules::ticks_per_month`, `Rules::months_per_year`, `Rules::ticks_per_year()`,
`Rules::is_month_boundary()`, `RawRules`'s two matching fields, their validation in
`sim-data/src/validate.rs` (the `< 1` checks and the `checked_mul` overflow check —
`ValidationErrorKind::YearTooLong` goes with it, since nothing constructs it once the product is a
compile-time `30 * 12`), and the two fields' bytes in `sim-core/src/data_hash.rs`.

Two zero-guards fall out as unreachable and are deleted rather than kept as dead defensiveness:
`Rules::is_month_boundary`'s `self.ticks_per_month != 0 &&` (a table-loaded `u32` could be zero;
`Calendar::TICKS_PER_MONTH` cannot) and `demographics::run`'s matching guard around `divisor`, which
becomes a `const` computed from `Calendar::TICKS_PER_MONTH`.

Every call site the field removal finds across `sim-core`'s and `sim-data`'s source and tests moves to
`Calendar::TICKS_PER_MONTH`/`TICKS_PER_YEAR`/`is_month_boundary`. `sim-data/data/rules.ron` and the
`satisfaction_out_of_range.ron` broken fixture drop the two lines. `RULES.md`'s "Time" section and its
`rules.ron` parameter table drop the two parameters (the file may name no table parameter that is not
in a table — `doc-check`'s `rules-parameters` check). `GLOSSARY.md` gains a **calendar** entry and a
`Calendar::TICKS_PER_MONTH`/`MONTHS_PER_YEAR` row in "Frozen strings and values", matching
`CHECKPOINT_EVERY`'s shape: the value is not hashed directly any more, but changing it still moves
every recorded replay, through the tick's own behaviour rather than through a hash byte.

`D6` (`plan/14.5.5-the-constitution.md`) gets its first dated amendment, appended below its own
paragraph, making the argument above in short form and pointing back here for the full one.
`plan/14.9.9.2-a-tick-cannot-be-mistaken-for-any-other-number.md` gets a short dated amendment where
it says *"sim-data is untouched: `RawRules`/`Rules::ticks_per_month` are both durations"* — the
instant/duration distinction it argued still holds, but that sentence's second half no longer
describes the tree.

## Out of scope

- `Tick` itself, and the instant/duration distinction 14.9.9.2 settled — `Calendar`'s constants stay
  plain `u32`, exactly as `ticks_per_month` was before this phase, for the same reason: they are a
  duration, never a moment.
- Any other field of `Rules`. This is not a reopening of `D6` in general; every other number in
  `rules.ron` stays there, because a designer genuinely might retune it.
- The dataset hash's *shape* beyond removing these two fields' bytes — no other field moves, no other
  byte order changes.
- `CHECKPOINT_EVERY`, the tick step order, or anything else already hardcoded outside a table; this
  phase adds one more instance of an existing, already-accepted pattern, not a new one.

## Tests

- Unit tests beside `Calendar` in `tick.rs`, mirroring `Tick`'s own: `is_month_boundary` at the
  boundary and just off it on both sides (0, 29, 30, 31); `TICKS_PER_YEAR == 360`.
- The full existing suite continues to pass, with call sites updated to read `Calendar` instead of
  `w.data().rules.ticks_per_month`/`.ticks_per_year()` — a mechanical substitution the compiler finds,
  the same shape 14.9.9.2's `Tick` change took.
- `cargo xtask regen-expected --check` green before starting; **not** green immediately after removing
  the two fields from `data_hash.rs` — that is the expected, single, deliberate reason to regenerate,
  and every recording is expected to diverge starting at its first checkpoint (tick 30), not partway
  through a run, which is the signature of a hash-*layout* change rather than a new source of
  non-determinism. Green again after `regen-expected`, and green a second time after that
  (idempotence), plus `cargo test -p sim-replay` for cross-process determinism.
- `cargo xtask doc-check` green, exercising the `RULES.md` edits directly: `rules-no-values` (no bare
  digit may appear in `RULES.md`) and `rules-parameters` (no backticked snake_case name in `RULES.md`
  may fail to match an actual `sim-data/data/*.ron` key, in either direction).

**Done when:** no `.rs` or `.ron` file in the tree names `ticks_per_month` or `months_per_year`,
`Calendar` is the one place either number is written, and every check above is green.

## How it went

**Built exactly as designed.** `Calendar` in `sim-core/src/tick.rs` is precisely the four-const,
one-method shape the plan sketched; every removal (`Rules`'s two fields and two methods, `RawRules`'s
two fields, `validate_rules`'s checks, `ValidationErrorKind::YearTooLong`, `data_hash.rs`'s two
`h.update` calls) and every call-site substitution across `sim-core`, `sim-data` and both crates' test
suites happened exactly where the plan named them, with the compiler finding every remaining site the
grep-based survey had already found in advance.

**Two small deletions the plan's "What gets built" did not itemise, both a direct consequence of the
substitution rather than new scope.** `xtask/src/expected.rs::expected_ticks(data: &DataSet) -> u32`
and `sim-replay/tests/expected.rs::until(data: &DataSet) -> Tick` both existed solely to read
`data.rules.ticks_per_year()`; once that became `Calendar::TICKS_PER_YEAR`, the `data` parameter each
took had nothing left to do, so both lost it (and `until`'s nine call sites lost `&data`). Left as
`_data: &DataSet` they would have been dead parameters explaining nothing; the plan's "the removal of
two `Rules` fields finds" language covered this in spirit but not by name.

**The regen-expected divergence matched the prediction precisely.** Before touching `data_hash.rs`,
`--check` was green. After removing the two fields' bytes, all four recording files (`minimal.ron`,
`minimal.hashes`, `hunger.ron`, `hunger.hashes`) needed regenerating, and every hash in both `.hashes`
files changed starting at tick 30 — the first checkpoint, not partway through a run — which is exactly
the signature the plan named as the mark of a hash-*layout* change rather than a new source of
non-determinism. `--check` was green twice more after regenerating, and `cargo test -p sim-replay`
passed all 13 tests.

**`cargo fmt --all --check` is clean for every file this phase touched.** Two unrelated diffs remain in
`sim-core/src/coverage.rs` (import ordering and a line-wrap) — the same pre-existing drift
`plan/14.9.9.2` recorded finding and leaving alone, predating this branch too, and left alone again for
the same reason: fixing it would not be one reason to regenerate, it would be a second one riding along
in the same commit.

**Docs.** `RULES.md`'s "Time" section and `rules.ron` parameter table were the one place `doc-check`
actually exercised the change (`rules-parameters`, `rules-no-values`) — both failed on the first run
with the fields removed from `rules.ron` but still named in `RULES.md`, exactly as predicted, and both
passed once the section was reworded without a snake_case backtick or a bare digit. `ARCHITECTURE.md`
took one line noting `Calendar` lives in `tick.rs`. `GLOSSARY.md` gained the **calendar** entry and the
`Calendar::TICKS_PER_MONTH`/`MONTHS_PER_YEAR` frozen-value row. `D6` took its first amendment ever, and
`plan/14.9.9.2` took two short ones, below the two sentences this phase made inaccurate.
