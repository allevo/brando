# Phase 16.9.6 — A generated map is the same thing as a loaded one

> See [How it went](#how-it-went) at the end, which is where the shape it really took is written
> down. Everything above that section is the plan as it was written, including the parts the work
> proved wrong — the prediction next to the outcome is the point.

**Goal:** `map-gen`'s public items are only `Config`, `Source`, `SourceKind`, `ConfigError` and
`generate`; `generate` returns the `MapDef` the game plays; and every map it generates is
byte-identical to what `draw` generated before.
**Depends on:** 16.9.5 — the first map the generator drew that is also played, which is what makes
"what the game can use" something the tree can check rather than a guess.
**Size:** S.

## Why now

Because the expected shape of the crate is *parse the flags into a configuration, call one function,
get back what the game plays*, and the crate is not that shape. `draw` returns
`Drawn { def: MapDef, repair: Repair }`, and every caller reaches through `.def`: the game needs
the `MapDef` alone — `Grid::from_map` takes it, `save_map` takes it, and a recording's map hash is
read off it. `repair` is two counters that only the report prints, and the report is a second public
entry point, `report(&Drawn, &DataSet)`, with public types of its own. It needs the gameplay tables,
so the generator knows about buildings and `max_build_slope`, and `gen-map` loads every table just to
print a summary. None of it is needed by the game, and all of it sits between the configuration and
the map.

## What gets built

- **`generate(&Config) -> Result<MapDef, ConfigError>`** replaces `draw`, in `lib.rs` beside the
  types it takes and returns; its body lists the passes in order. `DrawInput` becomes `Config` and
  `DrawError` becomes `ConfigError`, every variant of which is "the config is unusable"; the variants
  keep their names.
- **The checks** leave `pipeline.rs` for `check.rs`, which hands back the grid the passes read their
  geometry from. `pipeline.rs` goes; `SEA_LEVEL` moves to `lib.rs`.
- **The report moves to `xtask`**, as `map_report`: it reads a `MapDef` and the tables and nothing
  from inside the generator, so it is the tool's business. Its two tests move with it.
- **`Drawn` and `Repair` are deleted.** The repair returns nothing, and the report loses its
  `repair` line — the one thing this phase takes away.

## Out of scope

Anything that changes what a seed generates or what `gen-map` writes, including 16.9.5's list:
the header still leaves out the size flags, `run` still cannot name a map, the rock step still does
not follow `max_build_slope`. The passes keep their code, their draw order and their signatures.

## Tests

1. ***The test that defines the phase.*** The crate's own tests, reading `generate`'s `MapDef`
   directly, are green, and so are the report's in `xtask`.
2. ***The test that closes the phase.*** The same `gen-map` commands, before and after, write
   byte-identical files — `hills-and-sea`'s own among them, identical to the committed one — and
   `regen-expected --check` is green before and after.

## Verification

```sh
cargo xtask regen-expected --check          # before
cargo test --workspace
cargo xtask gen-map --seed 6 --width 48 --height 32 --id hills-and-sea --min-height 0 \
    --max-height 31 --source 4,4,mountain,3 --source 44,4,mountain,2 --source 4,28,sea,5 \
    --source 44,28,sea,4 --source 24,16,land,10 --out <scratch>/after.ron
cmp <scratch>/after.ron sim-data/maps/hills-and-sea.ron
cargo xtask regen-expected --check          # after: still green, nothing regenerated
cargo xtask doc-check
cargo fmt --all --check
cargo clippy -p map-gen -p xtask --all-targets
```

**Done when:** `map-gen` exposes only `Config`, `Source`, `SourceKind`, `ConfigError` and `generate`,
`generate` returns a `MapDef`, and every map it generates is byte-identical to before.

## How it went

**It held on the first pass, and the closing test is the reason to believe it.** Seven maps were
generated before the change and again after it — seeds 1 to 6 on `hills-and-sea`'s own sources, and a
small map on a narrower height range — and all seven files are byte-identical, `hills-and-sea`'s
identical to the committed one. The only line of any report that changed is the `repair` line, gone.
The passes were not touched, so this is what it should be; the test is what shows it.

**One of the moved assertions could never have failed.** The old repair test checked
`tiles_drowned + walkable >= walkable`, which holds for any two unsigned numbers. It left with the
counts it was reading; "the repair only ever drowns land" is pinned where it always really was, by
the repair's own unit test.

**The report's tests keep their sample exactly.** `map-gen`'s tests generate from a helper that
puts sources on the corners and the centre of any size; the report's tests in `xtask` cannot call a
helper in another crate's test file, so they spell out the five sources that helper produces at
48×32. They test what they tested before, on the same maps.

`ARCHITECTURE.md`'s `map-gen` row now says `generate` turns a `Config` into the `MapDef` the game
plays. `RULES.md` and `GLOSSARY.md` are unaffected: no rule changed, and none of the words that moved
— `draw`, `generate`, `report`, `repair`, `config` — is one the glossary defines.
