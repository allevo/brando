# Phase 16.7 — A source is typed, not just written

> See [How it went](#how-it-went) at the end, which is where the shape it really took is written
> down. Everything above that section is the plan as it was written, including the parts the work
> proved wrong — the prediction next to the outcome is the point.

**Goal:** `cargo xtask gen-map2` draws a map from sources given entirely as `--source` flags, with
no RON file written or read.
**Depends on:** 16.6 — the crate, the `Source`/`SourceKind` types, and the `gen-map2` front door
`--sources <path>` already reads a file through.
**Size:** S.

## Why now

Because the file was never the point — `map-gen2`'s own public API is `Vec<Source>`, and
`--sources <path>` is one way of building one, chosen in 16.6 because a list does not fit
comfortably as bare positional flags. A handful of sources typed straight into the shell is a
faster loop for trying a layout than opening an editor for a five-line file, and every other flag
`gen-map2` takes is already typed on the command line — the file was the one input that was not.

It takes a half number for the same reason 16.6 did: it touches nothing but `xtask`'s own front
door. `map-gen2` gains no new dependency and no new public type; this phase adds a second way to
build the `Vec<Source>` that already exists, not a new shape for it to take.

## What gets built

### `--source <x>,<y>,<kind>,<strength>`, repeated once per source

```
gen-map2 --seed <n> --width <n> --height <n> --id <name> --min-height <n> --max-height <n> \
         (--sources <file.ron> | --source <x>,<y>,<kind>,<strength> [--source ...]) \
         [--out <path>] [--print]
```

Comma-separated fields on one flag, repeated — the same shape `bench`'s own `--houses
1=2000,2=800` and `--places well=70,farm=150` already use for "more than one thing, one flag per
occurrence or one value list", read with `str::split(',')` the same way. `kind` is read
case-insensitively (`mountain`, `Mountain`, `MOUNTAIN` all name the same variant): a RON file
already has to spell the enum's exact declared name, and a CLI flag typed by hand should not carry
the same requirement for no reason a shell script would ever care about.

A new, repeatable-flag counterpart to `main.rs`'s existing `flag` helper, which only ever returns
the first occurrence of a name:

```rust
/// Every value passed after `name`, once per occurrence — `flag`'s
/// repeatable counterpart, for a flag meant to be given more than once.
fn flags(args: &[String], name: &str) -> Vec<String>;
```

### The two ways to name sources are mutually exclusive, and one of them is required

`--sources <path>` and one-or-more `--source ...` are refused together, and refused if neither is
given — the same discipline `bench.rs` applies to `--residents`/`--houses` overlapping: an
ambiguous combination of flags is a clean error naming the ambiguity, not a silent choice of which
one wins.

### The words

Nothing new: `source`, `strength` and the three kind names are already in `GLOSSARY.md` from 16.6.
This phase adds a second syntax for typing them, not a new concept.

## Out of scope

**Removing `--sources <path>`.** A file is still the better choice for a source list worth keeping
and reusing across runs, or one long enough that a shell command would be unreadable. Both stay.

**A third way to describe a map's relief** (noise mixed with sources, sources read from an
existing map, anything generative beyond what 16.6 already built). This phase is a CLI convenience
for the one input 16.6 already has, nothing more.

## Tests

1. ***The test that defines the phase.*** `gen-map2` given only `--source` flags (no `--sources`)
   draws the same map as the equivalent RON file given to `--sources` — the two front doors build
   the identical `Vec<Source>`, so nothing about which syntax was used can reach the map itself.
2. **Each malformed `--source` value is refused by name**: wrong field count, an unparseable `x`/
   `y`/`strength`, an unknown `kind`.
3. **`kind` is read case-insensitively**, pinned so a later change to the parser cannot quietly
   make it exact-match again.
4. **Giving both `--sources` and `--source` is refused**, and so is giving neither.

## Verification

```sh
cargo xtask regen-expected --check   # before
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings   # blocked by the pre-existing sim-core
                                                          # dead-code warning 16.6's "How it went"
                                                          # recorded; cargo clippy -p xtask
                                                          # --all-targets is the real signal here
cargo fmt --all --check
cargo xtask gen-map2 --seed 7 --width 48 --height 32 --id inline-test \
    --min-height 0 --max-height 31 --print \
    --source 4,4,mountain,3 --source 44,4,mountain,2 \
    --source 4,28,sea,5 --source 44,28,sea,4 --source 24,16,land,1
cargo xtask regen-expected --check   # after: still green
cargo xtask doc-check
```

**Done when:** a map can be drawn by `gen-map2` with no file written or read, the same map a
RON file with the same sources would have drawn, and the two ways of naming sources cannot be
combined by accident.

## How it went

**Everything went as planned, with one addition the plan did not name.** `note` — the comment
`gen-map2` writes atop a saved map, recording the command that drew it — quoted `--sources
<path>` unconditionally before this phase, which would have been a lie for a map drawn from
`--source` flags with no file at all. `read_sources` now returns the exact flag text that named
the sources alongside the parsed list, and `note` records whichever one really happened. This
was not a decision the plan weighed and got wrong; it simply did not consider the note at all,
and building the second code path surfaced it immediately.

**The defining test held on the first try.** A map drawn from five `--source` flags and the
identical map drawn from a RON file naming the same five sources came out byte-identical (checked
by diffing the rendered files, minus the `id` and the `note`'s command line, which differ by
construction). Nothing about which syntax was used reaches `map_gen2::draw` differently, which is
exactly the property `Vec<Source>` being the one real API and both front doors just building one
was supposed to guarantee.

**`cargo clippy --workspace --all-targets -- -D warnings` still cannot run clean**, for the exact
pre-existing, unrelated reason 16.6's own "How it went" already recorded: `sim-core`'s
`WalksToTheEnd` dead-code warning. `cargo clippy -p xtask --all-targets` is clean of anything in
this phase's own files. Left alone again, for the same reason: fixing another crate's latent issue
is not this phase's job.

`cargo test --workspace`, `cargo fmt --all --check`, `cargo xtask doc-check` and
`cargo xtask regen-expected --check` are all green, the last one unchanged before and after —
this phase touches only `xtask`'s own front door and adds nothing to `map-gen2`'s public surface,
so there was never anything for it to move.
